# 统一 AgentRAG DAG：做过什么、为什么删

**状态：已删除（2026-11-14，[ADR 0001](adr/0001-langgraph-runtime.md) 阶段 10）。** 本文是历史记录。v3 统一图的代码、测试和评测用例都不在仓库里了；删除之前的完整设计文本是提交 21eae0c6 上的这个文件（`git show 21eae0c6:docs/unified-agent-dag-migration.md`），代码在同一个提交的 `server/rag/agent-unified-*.js`。

## 它是什么

v3 统一图把一个请求的所有阶段（文档问答、证据检查、补检索、Web、内置 Skill、自定义 Skill、一个带审批门的 Capability）规划成同一张受治理的 DAG，由 `AGENT_UNIFIED_GRAPH_ROLLOUT` 控制：

- `off`（默认）：不用它，外层执行计划按固定顺序回答请求。
- `shadow`：旁路规划一张 v3 图并记录，答案仍由外层执行计划给出。
- `guarded`：通过准入的 v3 图回答整个请求；执行前被拒的由外层执行计划回答。

它不是第二个运行时（两种方式都在 LangGraph 上），是第二种回答请求的方式。默认值从来没有改成 `guarded`。

## 经过

- **2026-09-25**：custom Skill 阶段的 typed DAG 成为默认执行器，v3 统一图冻结在 `shadow`。解冻条件有两个：有外层固定顺序表达不了、且有评测用例证明的编排需求；四块跨进程恢复各有测试。
- **2026-09-27**：两轮解冻。第一轮开放 `guarded`，任何可能中途等用户确认的节点让整图在运行前被拒；第二轮图内审批续跑落地，含一个审批门 Capability 的图可以进图。
- **2026-10-14 到 10-16**：随 ADR 0001 迁到 LangGraph（阶段 3），原生图调度器删除后（阶段 6）只在 LangGraph 上调度。阶段 5 的结论是不设为默认：覆盖不了全部请求、被接管的请求行为会变、CPU 是外层计划的数倍、真实模型证据不足。
- **2026-11-14**：用户决定 agent 只留一种回答方式，v3 统一图整个删除（阶段 10）。

## 它做到了什么

这些都有确定性测试，证据类型是注入提案加 mock，证明的是运行时契约，不是答案质量：

- **整图准入**：任何节点执行前对整图判定，被拒的请求原样交给外层执行计划。数据边界是其中最重要的规则：有外部副作用的节点只读用户自己的问题，文档派生的文本不会发给第三方搜索；外部节点的输出不进任何其他节点的输入，只进最终答案。
- **外层固定顺序表达不了的编排**：Skill 只在文档答案通过证据检查之后运行，并把已验证的答案作为类型化输入交给它；证据不足时 Skill 跳过、不计费。外层执行计划里 Skill 先跑、无条件跑。
- **图内审批续跑**：带审批门的 Capability 停在干净边界，审批对象的 hash 覆盖精确输入并绑定 run、图摘要和节点；批准或拒绝之后在同一张图上续跑，Capability 最多执行一次。审批的任务内容来自已验证的文档答案。
- **跨进程恢复**：文档循环的状态从持久化输出重建、整次运行的 finalization 收据、节点边界续跑、审批续跑，共 7 个真实 PostgreSQL 上的跨进程用例。
- **两个 trajectory 用例和一个 planner 用例**进了质量门（manifest 1.13.0 到 1.17.0）。

## 量出了什么

- **真实模型规划（2026-09-27，本地 qwen2.5:7b，只有规划器调模型，15 次规划）**：模型自己的计划被接受 3 次，12 次换成确定性图，0 次由外层执行计划回答。回退原因：漏选意图的 Skill 6、无法投影 4、非法输出引用 4、缺审批授权 1。每次规划平均 8.1 秒、约 2,000 token。运行时契约（整图拒绝、兜底不部分执行）在真实模型下成立；模型的规划能力没有得到证明。
- **开销（2026-10-16，进程内微基准，内存 run store、mock RAG）**：一次文档问答的 CPU，外层计划约 0.8–1.2 ms，v3 在 LangGraph 上约 11–15 ms；带事件的写从 3 次到 10 次，另加 11 次无事件写。
- **覆盖**：research brief、arXiv 导入、没有常设授权的 Web 和文档发现、第二个审批门 Capability、不是意图本身动作的 Capability、外层计划所有的 run 的重入，v3 都答不了。

## 为什么删

- 用户要 agent 只有一种回答请求的方式。
- 让 v3 成为那一种，要先补齐它答不了的请求，而已有的数字不支持：规划慢、模型计划大多被拒、开销大、没有答案质量证据。
- 把它设成默认、留外层计划兜底，是两种方式同时在线上回答请求，和要求相反。
- 留着不用也有成本：清点时只有它走得到的代码是 22 个文件、8,108 行，测试 17 个文件加 44 份 golden，共用模块的每次改动都要让它的 golden 继续通过。

## 删除之后

- `AGENT_UNIFIED_GRAPH_ROLLOUT` 只接受未设置或 `off`；`guarded`、`shadow` 和其他任何取值拒绝启动（`AGENT_UNIFIED_GRAPH_ROLLOUT_REMOVED`）。`AGENT_UNIFIED_GRAPH_CAPABILITIES` 不再读取。
- 开过 `guarded` 的部署可能还存着 v3 的 run。已经结束的不动，续接它的请求新建一个 run。没结束的不能再续跑：启动恢复、审批端点和带 `agentRunId` 的重入都把它交给人，人可以取消。`server/rag/agent-removed-unified-graph.js` 是这部分的全部代码，`server/test/agent-stored-unified-graph-runs.test.mjs` 用 v3 代码当时写下的 run 记录逐种状态钉住。
- 失去的两种编排（证据检查之后才运行 Skill、审批内容来自已验证的答案）以后想要，得在外层执行计划里另做。
- 逐条行为、删了什么、怎样恢复，见 [ADR 0001](adr/0001-langgraph-runtime.md) 的“阶段 10 结果”。
