# 故障与决策故事

> 面试官最常追问的是"遇到过什么难题、怎么定位的"。下面每个故事都按"背景 → 发现 → 定位 → 修复 → 结果 → 学到了什么"组织，数字出处见 [CURRENT-TRUTH.md](CURRENT-TRUTH.md)。挑两三个讲熟，不要全讲。

## 故事 1：对比功能 100% 拒答，问题不在模型

- **背景**：第一次用真实模型（qwen2.5:7b）跑端到端检查，18 项过了 16 项，两项失败都在多文档对比：系统对"比较两份合同的责任上限"一律回答"证据不足"。
- **第一反应**：7B 模型能力不够。之前的离线自测也是 16/18，文档里当时的解释就是"替身模型的问题"。
- **定位**：在答案生成的三个阶段（模型文本 → 引擎模板兜底 → 拒答）加临时日志，发现**模型的答案其实是对的**（A 12 个月、B 6 个月、带引用），是我自己的 claim 校验器把 11 条 claim 全判成无支持。然后用控制变量实验一次只改一个因素：
  1. 模型写的引用是 `[Source 1, Source 3]`，解析器只认空格分隔，引用丢失，引用标签还被切成一条独立的"claim"。
  2. 同样的内容，文件名叫 `handbook-alpha.pdf` 能通过，叫 `vendor-a.pdf` 就失败。原因是只有含数字或特定名词（policy、contract 等）的文件名才被当成文档名，"vendor a" 被当成事实主语，两份文档的差异配不上对。
- **修复**：引用在模型输出进入系统时就统一归一化；变体后缀（`-a`、`_ii`、`-beta`）的文件名也视为文档名，同时保留"不剥离主题型文件名"的保护，并禁止把公共前缀 "vendor" 当成两份文档共用的别名。补了 7 个回归测试，其中一个专门确认修复没有放松"相同文档不能编造差异"。
- **结果**：16/18 → 18/18，离线自测也变成 18/18。被追问时要说清：现在 `verify:quality` 里的对比题是靠引擎按证据拼的模板通过的；2026-10-04 加上拒绝原因记录后测了两轮，qwen2.5:7b 自己写的对比答案仍全部以 `unsupported_claims` 被词法校验拒绝（概括句没标来源、差异句换了数值说法）。
- **学到**："模型不行"是最容易、也最危险的归因。先看每一阶段实际拒绝的是什么，再下结论。

## 故事 2：约束解码修好了格式，却让延迟涨了 10 倍

- **背景**：规划器在 7B 模型下 56% 的调用因为 JSON 格式或越界被降级。
- **修复一**：按请求从运行时白名单生成 strict JSON Schema（选中的 step、合法条件、Skill 的类型化输入输出、已授权文档都写成枚举）。降级率降到 16%。
- **新问题**：5 轮评测从 1 分钟变成超过 10 分钟。Ollama 日志里一次生成到了 3810 个 token 还在继续：模型在约束解码下进入不限长度的 `rationale` 字段后停不下来。
- **修复二**：所有自由文本和数组都加上限，长度用 `pattern` 而不是 `maxLength`（查了 OpenAI 文档，strict 模式没把 `maxLength` 列为支持）。同一个调用从 754 token / 15 秒降到 374 token / 7 秒。
- **又一个问题**：Ollama 的约束并不是硬保证，JSON 闭合后模型还会接着写中文，旧解析器（"第一个 `{` 到最后一个 `}`"）因此失败。改成提取第一个括号平衡的 JSON 值。另外 DAG 规划器会规划出超过剩余预算的节点，于是把"预算能支付的节点数"作为上限告诉规划器，schema 跟着收紧。
- **结果**：降级 56% → 8%，用例通过 47% → 80%，延迟回到 14 秒左右，和改前持平。
- **学到**：约束解码只约束"形状"，不约束"长度"和"是否停下"；每个改动都要同时量效果和延迟。另外，只修 prompt 的对照组几乎没有提升，这说明收益确实来自 schema。

## 故事 3：测试推翻了我自己的解释

- **背景**：做 LLM 调用容错时，我让代码遵守服务端的 `Retry-After`。故障注入评测里，没有备用模型时限流场景的成功率反而从 79% 降到 62–67%。
- **当时的解释**：遵守粗粒度的 `Retry-After: 1` 让重试更保守，抢不到令牌。我甚至准备在提交说明里这样写。
- **真正原因**：单元测试失败，暴露出 `Number(null)` 等于 0：没有 `retry-after-ms` 头时，解析器把它当成"立刻重试"，粗粒度的 1 秒根本没被遵守；变差是因为新的抖动退避总等待时间比旧版短。
- **修复**：先判断头是否存在再解析；退避基数调到 500ms，让平均总等待和旧版持平，这样这次改动只增加抖动和 Retry-After，不偷偷缩短等待。
- **结果**：无备用模型时粗粒度限流的成功率 94.4%，而且每次调用的请求数从 2.63 降到 2.08；带备用模型 100%。
- **学到**：解释先要被证伪一次再写进结论。评测数字异常时，先怀疑自己的代码。

## 故事 4：伪 embedding 给出了错误的架构结论

- **背景**：所有检索评测原本都用哈希词频的伪 embedding，结果显示 hybrid 检索（0.54）比单独 BM25（0.66）还差。
- **风险**：如果据此把默认改成 BM25，会是一个错误决定。
- **做法**：让对比脚本支持真实 embedding，并给每组差异加配对 bootstrap 置信区间。
- **结果**：真实 embedding 下 hybrid 反而是数值最好的（0.71），启发式 reranker 反而略降。同时置信区间显示，48 条用例下大多数差异不显著，于是我把"hybrid 更好"改成"数值最好、从不显著更差"，并开始接 QASPER 扩大评测集。QASPER 接入后（281 篇论文、821 个可回答问题），hybrid 比 BM25 +0.074 [+0.048, +0.102]，显著；比稠密 +0.006 [−0.019, +0.031]，不显著。48 条上"hybrid 比稠密高 0.057"的印象没有复现，结论收窄为"比单用 BM25 好"。
- **学到**：离线替身只能证明管道接通了，不能用来做效果结论；没有置信区间的排名不要讲。

## 故事 5：三个"不报错但悄悄算错"的 bug

来自做单机版时的排查，适合回答"最隐蔽的 bug"：

1. **BM25 统计被污染**：稠密索引写入失败后，稀疏索引里的条目没有回滚。这些条目参与全局 IDF 统计，悄悄影响了所有其它文档的打分。修复：失败时无条件回滚稀疏索引。
2. **跨维度打分**：换了 embedding 模型后，旧向量和新查询维度不同，却算出了 0.7071 的相似度，远高于 0.32 的相关性阈值，垃圾块被当成证据。修复：维度不一致直接拒绝，并对每种形状只告警一次。
3. **词法覆盖率否决所有对比问题**："比较责任上限"这类自然问法的覆盖率只有 0.50，阈值是 0.51，模型还没被调用就被拒了。修复：只对对比路径放宽，因为单文档问答里低覆盖率确实意味着答案不完整，全局放宽会让一个正确的拒答消失。

## 故事 6：修一个 bug 找到三个，指标却只动了一点

- **背景**：做流式草稿时用真实 7B 测，合同题 7 题里 6 题最后都在请用户澄清，连逐字引用合同的答案也被校验器拒绝。
- **定位**：用校验器同样的输入逐层复现，找到三件事：
  1. 合同写"twelve (12) months"，数值比较要求双方数字个数相同，所以"twelve months"永远对不上；
  2. 证据句子按每个换行切分，PDF 的排版换行把一句话切成两半；
  3. 这两个一起让校验退回 220 字符的摘录，而摘录恰好截断在要核对的数字前面。
- **修复**：同值的"词 + 括号数字"合并成一个数，不同值保留；额外检查软换行重新接起来的句子，按行切出的句子保留。第一版接换行的规则太宽，把标题也接到了正文上，一个"两份文档其实相同"的对照组开始误报差异，于是收紧成"下一行小写开头才算软换行"。
- **结果**：单元层面正确复述都能通过、错误数字照样拒绝，`verify:quality` 仍 18/18；但端到端合同题回答率只从 2/21 到 4/21。
- **学到**：bug 修对了不等于问题解决了，要回到端到端指标上看它解释了多少；这次剩下的主要是词法校验对改写太严，该换校验器而不是继续打补丁。对照组能抓住"修一个坏一个"。
- **后续**：之后试了几种新信号：LLM 评审（故事 7）、答案模型先判"证据里没有答案"、对这种标记的确定性复核，加上 7 个放宽开关。在 QASPER 上按事先定的规则测了三轮，答题率和 F1 都显著上升，但每一轮都会回答原本拒掉的不可答题（开发集上 0/9 → 2/9），三轮都没通过，默认一个没改。瓶颈是词法校验加 7B 模型；要两头都顾，需要更强的答案或评审模型。

## 故事 7：评测脚本冤枉了 LLM 评审

- **背景**：给 LLM 评审做校准，第一轮结果是错误接受 2/42，都是"加了一个条件"的句子，比如"…30 天书面通知，且通知须挂号寄出"。这正是 LLM 评审出了名的弱点，我准备改提示词、让它逐条列事实再判。
- **先验证再改**：改提示词会让结果贴合这套数据，所以先写了 8 条留出集，并用未改的评审再跑一遍作基线。
- **发现**：逐行看留出集的记录，发现词法校验会把"X，且 Y"拆成两条 claim，而我的评测只读了第一条。评审其实只接受了前半句，后半句被拒，finalizer 会删掉它。是评测脚本冤枉了评审。修正为"拆出的每条都通过才算接受"后，错误接受 0/42、留出集 0/12。
- **也看到了真实问题**：另一轮里"…unless the claim involves data loss"被接受过 1 次，理由写着"引入了原文没有的条件"，结论却是 supported。评审的结论字段偶尔和自己的理由矛盾，所以它只被允许升级、数字仍由规则把关，并且默认关闭，等人工标注校准。
- **结果**：端到端合同题从 3/21 到 14/21 得到回答，14 个全对，p50 多 0.8 秒。
- **学到**：指标变差时先怀疑测量；改模型之前先留出一份没被看过的数据。

## 故事 8：取消的调用被熔断器记成失败

- **背景**：做端到端截止时间（`AGENT_REQUEST_TIMEOUT_MS`）：截止时间从入口一路传到 agent、检索、网关和模型调用，到点后进行中的模型调用被中止，运行在下一个安全点以 `deadline_exceeded` 结束，应该答 504。
- **发现**：压测验证时（截止时间 300 ms、假模型 800 ms、并发 4/16），234 次运行里 226 次直接 503，不是 504。
- **定位**：503 来自熔断器。被截止时间取消的模型调用被记成了一次失败，5 次就把这个模型熔断 30 秒，进程里所有租户的调用都被挡住：几个截止时间短的请求，就能让别人的请求失败。
- **修复**：调用方自己取消的调用既不算失败也不算成功：取消说明不了模型能不能用。
- **结果**：同样的压测复测，234 次运行全部以 `deadline_exceeded` 结束（504），0 次 503；失败延迟 p50 309 / 322 ms（并发 4 / 16）；进行中的模型调用全部被中止，排空后在途 0。
- **学到**：加一种新的失败来源时，要看所有按失败计数的地方怎么对待它，"调用方不要了"不等于"依赖坏了"。这个缺陷是测量抓到的，熔断器是进程共享的状态，一个请求的错误分类会变成别人的故障。

## 故事 9：外层计划上 LangGraph 两次压测不过门

- **背景**：把编排运行时迁到 LangGraph.js（ADR 0001，分阶段、带开关），事先定了硬门：压测里每请求应用 CPU 和 p95 退化不超过 10%。最初把外层 V1 计划也编成了 StateGraph。
- **发现**：第一轮压测（pgvector、模型 0 ms、每档 3 次）每个 `/chat` 多约 1.2 ms CPU：并发 32 时每请求 CPU 3.93–4.26 → 5.27–5.47 ms（+29–35%），p95 125–138 → 165–169 ms。不过门。
- **定位**：剖析看到 LangChain core 每个节点调用都新建一个 `RunTree`，没有配置能关；空的 3–5 节点图底价 0.38–0.59 ms，而 10% 的预算只有 0.4 ms。这是结构性开销，不是调参能调掉的。
- **修复一**：外层计划不需要持久状态和中断（它的持久化就是 run 的 step），所以留在原生循环；LangGraph 只调度需要它的 custom-Skill DAG 和 v3 统一图，外层计划图放到实验开关 `AGENT_OUTER_PLAN_RUNTIME` 后面。复测通过：并发 32 每请求 CPU 3.78–4.20 → 3.82–4.34 ms，区间重叠。
- **再试一次**：收尾阶段想把外层计划的开销削下来：改用底层 Pregel，按计划形状只编译一次，静态剪掉未选中的内置阶段。每次调用的 `RunTree` 54 → 2，进程内多出的开销从 1.23 ms 降到 0.28 ms。但 native 和 langgraph 交替跑四轮、每轮 5 次，并发 1 时每请求 CPU 中位数 5.68 → 6.68 ms（+17.6%），p95 9.3 → 10.5 ms（+13%），仍不过门；并发 32 同一配置不同轮次就漂移约 15–20%，不下结论。剩下的是 Pregel 每次调用固定要做的事（执行循环、任务 id、checkpoint 对象），在库内部（剖析见 ADR 0001 阶段 5）。
- **结果**：不放宽 10% 的门（用户认可），外层计划长期留在原生循环，LangGraph 实现只留作实验开关；只有 LangGraph 升级后单次调用开销明显下降，才按同样的方法重测。
- **学到**：框架迁移要先定硬性的性能门；门禁抓到结构性开销时，结论是"只把需要 checkpoint 和中断的图交给框架"，而不是放宽门或硬调过去。进程内微基准（+0.28 ms）会低估真实请求的开销（压测并发 1 约 +1 ms；ADR 推断是请求间有空闲，没有单独测量）。
