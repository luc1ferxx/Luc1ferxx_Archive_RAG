# 高频追问

> 每个回答先给一句结论，再给能指到代码或数字的依据。数字出处见 [CURRENT-TRUTH.md](CURRENT-TRUTH.md)，完整故事见 [NARRATIVE-CASES.md](NARRATIVE-CASES.md)。

## Agent 设计

### 1. 这是 Agent 还是 workflow？为什么不用 ReAct？

是"规划 + 执行"的 Agent，外层步骤由 LLM 在白名单里规划，自定义 Skill 阶段是模型规划的 typed DAG。没有用开放式 ReAct 循环，理由有三个：文档场景要求每一步可审计、可复现；成本和步数必须有上限（预算写死在运行时，重规划最多 1 次）；有副作用的操作需要在执行前过审批和重放安全检查，开放循环很难在执行前知道要做什么。代价是灵活性差一些，所以保留了有界的补检索和一次重规划。

### 2. 模型输出不可控怎么办？

三层：约束解码（按请求生成的 strict JSON Schema，白名单写成枚举）→ 容错解析（取第一个完整 JSON 值）→ 校验器整体接受或拒绝，拒绝就降级到确定性规划器。7B 模型下降级率从 56% 降到 8%。校验器是最终裁决，因为不是所有 OpenAI 兼容端点都真正执行 schema，Ollama 就不是硬保证。

### 3. 怎么防止模型越权调用工具？

规划器能看到的只有经过裁剪的能力描述、已授权文档 id 和问题，看不到用户身份、`accessScope` 和凭据；执行规划器只能在本次请求选中的步骤里挑。DAG 规划结果里如果出现审批、预算、`accessScope` 之类的运行时字段，校验器会整图拒绝，而不是悄悄删掉，否则等于告诉模型"要权限不花代价"。真正执行时，每个读文档的 Skill 都带着运行时的 `accessScope` 重新校验。

### 4. 运行到一半崩了怎么办？怎么保证不重复执行有副作用的步骤？

运行状态、步骤、事件和 guarded 图的 checkpoint 都存在 PostgreSQL。启动时只在节点边界自动续跑，而且要求没有待审批项、checkpoint 与已持久化的步骤对账一致。认领、节点开始、完成都带运行版本号做 CAS，旧 worker 写不进去。写文档记忆这类步骤标记为不可重放，只能人工显式重试。思路和 Temporal、LangGraph checkpointer 类似，区别是我把"哪些步骤可以自动重放"做成了由 Skill 契约声明、由运行时复核的矩阵。

### 5. 记忆怎么设计的？

分三层：run 内的工作记忆（查询去重、claim 支持、缺口，run 结束即丢弃）、会话记忆（用于改写追问）、长期记忆和经验记忆（只作为规划提示，永远不作为证据或引用）。原则是记忆不能变成答案的来源，答案证据只能来自本次检索到的文档。

## 检索与答案质量

### 6. 检索怎么做的？效果如何？

dense（pgvector 余弦）和 sparse（PostgreSQL 全文检索，不是 BM25）两路独立召回，RRF 融合，可选 rerank 放在融合之后。真实 embedding 下全量 Recall@5：hybrid 0.71、dense 0.65、BM25 0.66。但配对置信区间显示全量上的差异不显著，只有 tuning 子集上 hybrid 比 BM25 显著更好，所以我的说法是"数值最好、从不显著更差"。

### 7. 为什么 rerank 默认关闭？

真实 embedding 下，启发式 reranker 在三个子集里都没有带来提升，全量还降了约 5 个点（不显著）。神经交叉编码器的接入已经有了，下一步在更大的评测集上测它。

### 8. 幻觉怎么控制？

生成时要求保留证据原文的措辞和数值；生成后逐条 claim 核对引用是否支持；有缺口补检索一轮；finalizer 删除仍然没有支持的内容；多文档对比时还要求每个数值绑定到正确的文档。已知局限：校验器是词法的，认不出语义等价的改写，所以对比答案目前走模板兜底。改进方向是用 NLI 或经过人工校准（报告 Cohen's kappa）的 LLM 评审替换。

### 9. 你怎么评测一个 Agent？

分层：检索层看 Recall@K、NDCG，带配对置信区间；答案层做端到端检查，其中故意放了两个对照组，防止"总是拒答"或"总是找到差异"的系统蒙混过关；轨迹层检查选对了 Skill、有没有补检索、澄清和预算行为；规划层对真实模型重复跑多轮统计降级率；可靠性层做故障注入。这些都能在本地用真实模型复现。

### 10. 为什么一开始的评测不可信？

最初所有评测都用哈希词频的伪 embedding，它能证明管道接通，但不懂语义。在它下面 hybrid 比 BM25 差很多，换成真实 embedding 后结论完全反过来。教训是：离线替身只用来测管道，效果结论必须来自真实模型，并且要带置信区间。

## 工程与可靠性

### 11. LLM 调用失败怎么处理？

带抖动的指数退避，平均总等待和旧的固定间隔持平；服务端的 `retry-after-ms` / `Retry-After` 作为下限，再分散最多一半；超过 10 秒的等待直接放弃；请求超时也按可重试错误处理；空响应重试一次；重试用完后经模型注册表切换到备用模型，所以工作区策略同样约束备用模型，400/401、策略拦截和预算拦截不切换。故障注入下限流成功率 79% → 100%，主模型宕机 0 → 100%。之后又加了熔断：主模型连续 5 次不可用就熔断 30 秒，期间直接走备用模型，主模型宕机时每次调用的请求数从 5 降到 1.3，p50 从 2.6 秒降到 24 毫秒。

### 12. 429 也切换备用模型，不会加重拥塞吗？

会，这是有意的取舍。限流通常按模型计，备用模型往往有独立配额；但如果两者共用一个限流器（我的评测正是这种最坏情况），切换会给已经过载的端点加请求。持续过载靠重试兜不住，所以后来加了每个模型端点的并发上限：模拟自托管服务饱和时，改前 42% 的请求是超时后的重试，服务端还在处理客户端已放弃的请求；加上限后服务端队列从 16 压到 8，没有一次重试，p95 从 5.2 秒降到 3.2 秒。熔断器只统计 5xx、超时和连接错误，不统计 429，因为 429 说明服务在线，交给退避处理。还没做的是按 429 自适应调整上限（类似 TCP 的 AIMD）。

### 13. 为什么不流式输出 token？

finalizer 会在生成之后删掉没有证据的 claim，如果边生成边推 token，用户会先看到后来被删掉的内容。所以 `/chat/stream` 用 SSE 推每一步的进度摘要（规划、检索、自检），经校验的最终答案整体发送；客户端断开不会中断运行，避免留下写了一半的持久化运行。

### 14. 成本和延迟？

本地 7B 下，一轮 6 个用例的规划器评测约 14 秒；用 OpenAI 的 text-embedding-3-small，8 篇论文语料嵌入一次约 14.5 万 token，按标价约 0.003 美元（完整的检索对比会重复嵌入 9 次，约 0.017 美元）。我没有生产流量，所以没有真实的单次查询成本分布。能保证的是上限：每次运行除了次数预算，还有 token、成本、时长三个上限（默认 10 万 token、0.5 美元、5 分钟），按每次成功的模型调用计量，调用深在检索服务里也能通过 AsyncLocalStorage 记到发起它的运行上。用完后不再开始新工具，走已有的降级路径，而不是报错；已经开始的步骤会跑完，所以是软截止。默认值是按次数预算推算的防失控上限，不是按真实流量校准的。延迟用 OpenTelemetry 看：一次运行是一条 trace，每个规划器、每个 Skill、每次模型调用都是一个 span，带 token 数，能直接看出时间花在哪一步（本地 7B 下编排本身是毫秒级，时间几乎全在模型调用上）。

### 15. Prompt 注入怎么防？

目前是设计层防御：规划器看不到用户身份和凭据；文档范围、预算、审批都由运行时决定，文档里的注入无法扩大权限；外部搜索查询会过滤敏感实体；重规划器只看节点状态（是否拒答、引用数量），看不到检索到的内容，所以文档里的注入到不了决定下一步工具的组件。还没做的是对抗性测试集（投毒 PDF）和攻击成功率统计，这是下一步。

### 16. 你的灰度门禁一直不过，最后怎么把 DAG 转正的？

发现门禁把两个决定绑在了一起：用哪个执行器，和由谁来规划。原门禁要求真实 LLM 规划零降级，7B 模型达不到；但 LLM 规划失败时退回的是确定性 DAG，不是 V1 链，所以 LLM 的规划质量不影响 DAG 执行器本身是否安全。我把两者拆开：执行器转正看执行语义的证据（全量测试、轨迹、恢复评测、PostgreSQL 跨进程恢复测试），纯 LLM 规划的门禁保留原样，继续衡量模型。转正后用真实模型复测，规划器结果在噪声内不变，普通问答也没有被多加 Skill 阶段。拆开门禁本身也有风险，所以我专门查了行为变化最可能出问题的地方，而不是只看总通过率。

### 17. 可观测性怎么做的？为什么不直接打日志？

日志回答"发生了什么"，trace 回答"这次请求的时间花在哪一步、哪次模型调用、用了多少 token"。我用 OpenTelemetry 按 GenAI 语义约定打 span：一次运行一个 `invoke_agent`，下面是规划器、每个 Skill 的 `execute_tool`，Skill 里的每次模型调用是 `chat` span，带 token 和估算成本，重试是事件。用 OTLP 导出，所以 Phoenix、Langfuse、Jaeger 都能接，不绑定厂商。三个细节：一是 span 靠 AsyncLocalStorage 嵌套，检索服务深处的模型调用自动挂在发起它的 Skill 下面，不用一层层传参；二是不记录问题、prompt、输出和文档内容，因为 trace 后端是一个新的泄露面，测试会检查；三是 Phoenix 的 OTLP/HTTP 只收 protobuf，最初我装的导出器发 JSON，会被静默拒绝，查文档后改成默认 protobuf、按标准变量可切 JSON。

## 反思

### 18. 如果重来，你会怎么做？

更早接真实模型评测：之前花了很多时间做报告谱系、门禁这些"证据流程"，但评测数据本身只有几十条，流程比数据先进。也会更早收敛架构：之前 V1 顺序链、V2 typed DAG、v3 统一图三代并存，最近才把 V2 转成默认执行器、把 v3 冻结在 shadow，V1 只留作整图被拒时的兜底。

### 19. 项目里哪部分是你自己设计的？用了 AI 编码工具吗？

用了，这点坦白说。我负责的是设计决策和验证：比如"模型只提议、运行时决定"的边界、哪些步骤允许自动重放、用什么指标判断改动有没有用、什么时候不相信一个数字。面试里任何一个模块，我都应该能讲清楚为什么这样设计、怎么证明它有效。
