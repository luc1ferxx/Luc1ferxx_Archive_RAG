# 高频追问

> 每个回答先给一句结论，再给能指到代码或数字的依据。数字出处见 [CURRENT-TRUTH.md](CURRENT-TRUTH.md)，完整故事见 [NARRATIVE-CASES.md](NARRATIVE-CASES.md)。

## Agent 设计

### 1. 这是 Agent 还是 workflow？为什么不用 ReAct？

是"规划 + 执行"的 Agent，外层步骤由 LLM 在白名单里规划，自定义 Skill 阶段是模型规划的 typed DAG。没有用开放式 ReAct 循环，理由有三个：文档场景要求每一步可审计、可复现；成本和步数必须有上限（预算写死在运行时，重规划最多 1 次）；有副作用的操作需要在执行前过审批和重放安全检查，开放循环很难在执行前知道要做什么。代价是灵活性差一些，所以保留了有界的补检索和一次重规划。

### 2. 模型输出不可控怎么办？

三层：约束解码（按请求生成的 strict JSON Schema，白名单写成枚举）→ 容错解析（取第一个完整 JSON 值）→ 校验器整体接受或拒绝，拒绝就降级到确定性规划器。7B 模型下降级率从 56% 降到 8%。校验器是最终裁决，因为不是所有 OpenAI 兼容端点都真正执行 schema，Ollama 就不是硬保证。

### 3. 怎么防止模型越权调用工具？

规划器能看到的只有经过裁剪的能力描述、已授权文档 id 和问题，看不到用户身份、`accessScope` 和凭据。执行规划器只能在本次可用的阶段里挑：意图选中的阶段（选了文档问答时还能带上条件触发的 Web 兜底），加上默认 `guarded` 下有已授权原子 Skill 时的 `custom_skills`，所以模型可以给意图没选自定义 Skill 的请求加上这个阶段；不在其中的阶段被直接丢弃。DAG 规划结果里如果出现审批、预算、`accessScope` 之类的运行时字段，校验器会整图拒绝，而不是悄悄删掉，否则等于告诉模型"要权限不花代价"；整图拒绝只针对 DAG。真正执行时，每个读文档的 Skill 都带着运行时的 `accessScope` 重新校验。

### 4. 运行到一半崩了怎么办？怎么保证不重复执行有副作用的步骤？

运行状态、步骤、事件和 guarded 图的 checkpoint 都存在 PostgreSQL。启动时只在能证明安全时自动续跑，都要求没有待审批项，只有三种情形：外层计划恰好只有 `custom_skills` 一个阶段的 guarded custom-Skill 图，和走 guarded 路径的 v3 统一图（rollout 仍是 `guarded`，认领前还要核对 LangGraph 线程），这两种只在节点边界续跑，还要求 checkpoint 与已持久化的步骤对账一致，在途节点转人工；再就是没有图 checkpoint 的 run 里中断的 `custom_skill` 步骤，整步重放，矩阵里只有它标成可自动重放。普通文档问答 run 不自动续跑：`document_rag` 会写会话记忆，在途的一律转人工；这类步骤和 Capability 调用都标记为不可自动重放，只能人工显式重试。认领、节点开始、完成都带运行版本号做 CAS，挡住的是旧 worker 的状态写，不是它已经发出的副作用。custom-Skill DAG 和 v3 图现在由 LangGraph.js 调度：checkpointer 是写现有 run 行的自定义 `RunStoreCheckpointSaver`，v3 审批用 `interrupt()` + `Command({resume})` 在同一线程续跑；权威仍是自己的图 checkpoint，线程只存回执，两者对不上就转人工。能否自动重放由运行时按步骤类型登记的矩阵决定，Skill 契约的声明只能收窄、不能放宽。要主动说的缺口：run 没有租约，多实例部署时一个实例重启会把别的实例正在跑的 run 也当成中断（读代码推断，没测过）。

### 5. 记忆怎么设计的？

分三层：run 内的工作记忆（查询去重、claim 支持、缺口，run 结束即丢弃）、会话记忆（用于改写追问）、长期记忆和经验记忆。原则是记忆永远不作为证据或引用，答案证据只能来自本次检索到的文档。但记忆会影响过程：长期记忆（偏好和用户记下的笔记）会进追问改写和答案 prompt 的偏好块，并标明不能当文档证据；经验记忆只作规划提示，但能给意图候选重排、补入白名单里的意图，所以会改变确定性规划器的选择。写入只记录用户自己说的话：补检索、研究简报的子问题、Skill 拼出来的 prompt 和后台任务的中间轮次都不写。开鉴权时会话键按租户派生（`tenant:` + 用户、workspace、session id 的哈希），只拿到别人的 session id 读不到；长期记忆默认按用户，可以设 `LONG_MEMORY_SCOPE=workspace` 按 workspace 隔离。

## 检索与答案质量

### 6. 检索怎么做的？效果如何？

dense（pgvector 余弦）和 sparse 两路独立召回，RRF 融合，可选 rerank 放在融合之后。sparse 默认是在 PostgreSQL 里自建统计的 Okapi BM25，可切回 `ts_rank_cd`；QASPER 上两者没有显著差异，默认用 BM25 是产品决定。效果以外部标注的 QASPER 为主（dev 821 题，按段落算 Top-5，nomic）：hybrid 0.517、dense 0.511、BM25 0.442；hybrid 比 BM25 +0.074，显著；比 dense +0.006，不显著。所以我的说法是"hybrid 比单用 BM25 好"，不说"比稠密好"。更早的自建 48 条用例上 hybrid 0.71、dense 0.65、BM25 0.66，全量差异都不显著，只有 tuning 子集上 hybrid 比 BM25 显著更好，只作历史补充。

### 7. 为什么 rerank 默认关闭？

真实 embedding 下，启发式 reranker 在三个子集里都没有带来提升，全量还降了约 5 个点（不显著），QASPER 上也没有帮助。神经交叉编码器（bge-reranker-v2-m3）已在 QASPER dev 上测过：证据进入模型上下文 0.353 → 0.417，+0.063，显著；可回答题拒答 −4.4 个百分点，显著；答案 F1 +0.008，不显著。默认关是因为它要单独的模型服务，所以只作为有条件时的推荐配置。开重排时拒答门改看重排概率，可回答题拒答 37.8% → 13.9%，但不可回答题识别 80% → 45%。

### 8. 幻觉怎么控制？

生成时要求保留证据原文的措辞和数值；生成后逐条 claim 核对引用是否支持；有缺口补检索一轮；finalizer 删除仍然没有支持的内容；多文档对比时还要求每个数值绑定到正确的文档。词法校验几乎不放过编造，但也拒绝正确改写，本地 7B 下合同题 21 次只答了 3 次。所以加了受限的 LLM 评审：只复核被词法拒绝的 claim、只能升级不能降级，引用错误和证据里没有的数字仍由确定性规则直接拒绝，评审失败就保留词法结论。打开后合同题 14/21 得到回答且全对，代价是每个答案多一次调用。它默认关闭，因为评审用的是同一个 7B 模型，构造对照集上错误接受 0/54，但我观察到过它的结论和自己的理由相矛盾；上线前要用人工标注的真实答案报告 kappa。更直接的证据来自 Agent 路径上的 QASPER train 50 题：只开评审，可答题回答 10/41，但不可答题被回答 0/9 → 2/9，7 个开关全开再加评审是 4/9；之后加"先判断证据里有没有答案"和确定性复核又测了两轮，每轮都多答了不可答题，三轮都没过事先定的规则，所以默认不改。

### 9. 你怎么评测一个 Agent？

分两类，各证明各的。效果层用真实模型（本地 qwen2.5:7b 和 nomic）和外部标注的 QASPER，比较两组时带配对置信区间：检索层看 Recall@K、证据段落是否进候选；答案层看官方 F1 和拒答，答案引用里的证据和模型上下文里的证据分开统计；端到端检查里故意放了两个对照组，防止"总是拒答"或"总是找到差异"的系统蒙混过关；规划层对真实模型重复跑多轮统计降级率；提示注入红队也用真实模型。契约层用 mock：轨迹层（选对 Skill、补检索、澄清、预算）、规划器 mock 和恢复评测用的是脚本化的 ragService 或 mock provider，只证明编排行为，不证明效果；可靠性层用本地假服务做故障注入。`quality:current` 门禁要求这些确定性报告来自当前提交、干净工作区。

### 10. 为什么一开始的评测不可信？

最初所有评测都用哈希词频的伪 embedding，它能证明管道接通，但不懂语义。在它下面 hybrid 比 BM25 差很多（0.543 对 0.658），换成真实 embedding 后排序反过来，但 48 条用例全量上差异不显著，"hybrid 比 BM25 好"的显著结论来自后来接入的 QASPER。所以伪 embedding 下的排序是错的，不能用来做架构决策。教训是：离线替身只用来测管道，效果结论必须来自真实模型，并且要带置信区间。

## 工程与可靠性

### 11. LLM 调用失败怎么处理？

带抖动的指数退避，平均总等待和旧的固定间隔持平；服务端的 `retry-after-ms` / `Retry-After` 作为下限，再分散最多一半；超过 10 秒的等待直接放弃；请求超时也按可重试错误处理；空响应重试一次；重试用完后经模型注册表切换到备用模型，所以工作区策略同样约束备用模型，400/401、策略拦截和预算拦截不切换。故障注入下限流成功率 79% → 100%，主模型宕机 0 → 100%。之后又加了熔断：主模型连续 5 次不可用就熔断 30 秒，期间直接走备用模型，主模型宕机时每次调用的请求数从 5 降到 1.3，p50 从 2.6 秒降到 24 毫秒。

### 12. 429 也切换备用模型，不会加重拥塞吗？

会，这是有意的取舍。限流通常按模型计，备用模型往往有独立配额；但如果两者共用一个限流器（我的评测正是这种最坏情况），切换会给已经过载的端点加请求。持续过载靠重试兜不住，所以后来加了每个模型端点的并发上限：模拟自托管服务饱和时，改前 42% 的请求是超时后的重试，服务端还在处理客户端已放弃的请求；加上限后服务端队列从 16 压到 8，没有一次重试，p95 从 5.2 秒降到 3.2 秒。熔断器只统计 5xx、超时和连接错误，不统计 429，因为 429 说明服务在线，交给退避处理。还没做的是按 429 自适应调整上限（类似 TCP 的 AIMD）。

### 13. 为什么不流式输出 token？

finalizer 会在生成之后删掉没有证据的 claim，边生成边推 token，用户会先看到后来被删掉的内容。我的做法是推"校验过的草稿"：模型照常流式生成，token 不出服务器，每写完一句就用 finalizer 同一套校验检查已生成的前缀，通过的句子才推给界面，标成"已校验、可能调整"，最终答案到了整体替换。一开始我以为能保证"推出去的不会撤回"，读代码发现做不到：自检失败后会补检索、可能换答案或改成澄清，finalizer 也会重写整段，所以保证只能是"不展示未经校验的内容"，并用评测量撤回率。还踩了一个坑：句号先于"[Source 1]"到达，按句号切会在引用到之前把句子判成无支持，所以要等引用和下一个字符都到了才算一句写完。用真实 7B 量下来几乎没收益，19 题里只有 1 题产生草稿，因为词法校验器拒绝了大部分答案。顺着查出两个校验器 bug（合同里的"twelve (12)"被算成两个数；证据在 PDF 换行处被切断），修完后合同题的回答率从 2/21 到 4/21，提升很小。这说明 bug 是真的，但主要瓶颈是词法校验本身对改写用词太严。之后做了受限的 LLM 评审（第 8 题），在 QASPER 上没过事先定的规则，默认关；NLI 仍是候选，没测。

### 14. 成本和延迟？

本地 7B 下，一轮规划器评测约 14 秒（当时是 6 个用例，现在 7 个，没重测）；用 OpenAI 的 text-embedding-3-small，8 篇论文语料嵌入一次约 14.5 万 token，按标价约 0.003 美元（完整的检索对比会重复嵌入 9 次，约 0.017 美元）。我没有生产流量，所以没有真实的单次查询成本分布。能保证的是上限：每次运行除了次数预算，还有 token、成本、时长三个上限（默认 10 万 token、0.5 美元、5 分钟），按每次成功的模型调用计量。单体里调用深在检索代码里也能通过 AsyncLocalStorage 记到发起它的运行上；拆分部署时 AsyncLocalStorage 不跨进程，检索层在答案里带回 usage 记到运行上，网关调用由调用方写一条 mirror 事件，所以上限跨层也成立。用完后不再开始新工具，走已有的降级路径，而不是报错；已经开始的步骤会跑完，所以是软截止。默认值是按次数预算推算的防失控上限，不是按真实流量校准的。延迟用 OpenTelemetry 看：一次运行是一条 trace，每个规划器、每个 Skill、每次模型调用都是一个 span，带 token 数，能直接看出时间花在哪一步（本地 7B 下编排本身是毫秒级，时间几乎全在模型调用上）。

### 15. Prompt 注入怎么防？

三层防护都已实现、默认开启，并用自建红队集量过攻击成功率。第一层是确定性筛查：文档、文件名、网页结果进 prompt 前，把对 AI 说话的句子替换成标记；第二层是答案、网页回答、claim 评审的 prompt 写明证据是不可信数据；第三层是输出链接守卫，删掉图片和模型没见过的链接。底下还有设计层的兜底：规划器看不到用户身份、凭据和文档正文；文档范围、预算、审批都由运行时决定，文档里的注入无法扩大权限；外部搜索查询会过滤敏感实体；重规划器只看节点状态（是否拒答、引用数量），看不到检索到的内容。`eval:prompt-injection`（qwen2.5:7b，13 个攻击用例、7 类，每组 3 轮）：文档 RAG 答案里攻击进入答案 17/39 → 0/39，受攻击时仍给出正确事实 22/30 → 30/30。只加 prompt 规则时指令覆盖类仍 9/9，起决定作用的是确定性筛查，它在 16,001 句良性语料上误判 0 句。局限要主动说：刻意绕开模式的英文改写在文档 RAG 上改前改后都是 3/3 成功；用例是自己构造的、数量小，没用第三方基准测过；Agent 路径的 0/39 很大程度上是 7B 以澄清结束、答案被扣下了。

### 16. 你的灰度门禁一直不过，最后怎么把 DAG 转正的？

发现门禁把两个决定绑在了一起：用哪个执行器，和由谁来规划。原门禁要求真实 LLM 规划零降级，7B 模型达不到；但 LLM 规划失败时退回的是确定性 DAG，不是 V1 链，所以 LLM 的规划质量不影响 DAG 执行器本身是否安全。我把两者拆开：执行器转正看执行语义的证据（全量测试、轨迹、恢复评测、PostgreSQL 跨进程恢复测试），纯 LLM 规划的门禁保留原样，继续衡量模型。转正后用真实模型复测，规划器结果在噪声内不变，普通问答也没有被多加 Skill 阶段。拆开门禁本身也有风险，所以我专门查了行为变化最可能出问题的地方，而不是只看总通过率。

### 17. 可观测性怎么做的？为什么不直接打日志？

日志回答"发生了什么"，trace 回答"这次请求的时间花在哪一步、哪次模型调用、用了多少 token"。我用 OpenTelemetry 按 GenAI 语义约定打 span：一次运行一个 `invoke_agent`，下面是规划器、每个 Skill 的 `execute_tool`，Skill 里的每次模型调用是 `chat` span，带 token 和估算成本，重试是事件。用 OTLP 导出，所以 Phoenix、Langfuse、Jaeger 都能接，不绑定厂商。三个细节：一是 span 靠 AsyncLocalStorage 嵌套，检索服务深处的模型调用自动挂在发起它的 Skill 下面，不用一层层传参；拆分部署时服务客户端注入 W3C `traceparent`、接收端恢复，跨层仍是一条 trace；二是不记录问题、prompt、输出和文档内容，因为 trace 后端是一个新的泄露面，测试会检查；三是 Phoenix 的 OTLP/HTTP 只收 protobuf，最初我装的导出器发 JSON，会被静默拒绝，查文档后改成默认 protobuf、按标准变量可切 JSON。

### 18. 为什么只把两张图交给 LangGraph，外层计划不迁？

因为只有这两张图需要框架提供的东西：持久状态和中断。custom-Skill DAG 和 v3 统一图要在节点边界续跑，v3 还要在审批节点暂停、批准后同一线程续跑，所以交给 LangGraph.js；外层计划的持久性本来就是 run 的步骤，不需要 checkpoint 和中断，交过去只有开销。迁移前定了硬门：压测每请求 CPU 和 p95 退化都不超过 10%。第一次把外层计划也编成 StateGraph，并发 32 时每请求 CPU +29–35%；剖析下来是 LangChain core 每个节点调用都新建一个 `RunTree`，空的 3–5 节点图底价 0.38–0.59 ms，而 10% 的预算只有 0.4 ms，属于结构性开销。改用底层 Pregel 后进程内只多 0.28 ms，但压测并发 1 时每请求 CPU 仍 +17.6%，所以不放宽门，外层计划长期留在原生循环。两张图的原生调度器已删除：删除前把它在固定场景上的输出冻结成 golden（8 个套件、102 个文件），之后只在 LangGraph 上跑、对照 golden。取消走 drain，不把请求 signal 交给 LangGraph，因为直接交会让在途节点被重跑。

### 19. 多租户怎么隔离？哪些默认没开？

两层：应用层每个 store 按 user/workspace 过滤；PostgreSQL 行级安全再兜一层。鉴权后的中间件把访问范围放进 `AsyncLocalStorage`，带范围的语句在短事务里切到租户角色并设置租户变量，策略拒绝别的租户的行；后台任务和恢复以记录自己的范围执行。它防的是漏写过滤条件的 bug：2026-09-25 关掉它测，漏写过滤条件的查询在当时 9 张表上全部泄露（9/9，9728 行），打开后 0/9；伪造插入、跨租户更新删除这类越权读写 5/5 → 0/5。真实踩过的坑有两个：全文检索的 `@@` 不是 leakproof，行级安全下用不上 GIN，10 万分块、1000 篇文档时租户的 sparse p50 要 142 ms，改成先按租户过滤文档 id、再交给表所有者运行的排序函数，降到 19 ms；workspace 权限匹配不区分大小写，数据库租户却用请求头原值，只被授权访问 `acme` 的 token 发 `ACME` 就进了另一个租户，已修。之后又做了成员关系检查、按租户限流和配额、擦除和导出、回收站、审计哈希链、按租户的信封加密（擦除工作区时销毁它的密钥）。要主动说哪些默认关：API 鉴权、RBAC、成员关系检查、strict 租户上下文和数据库角色拆分、数据访问审计、加密都默认关；默认 lenient 下租户上下文丢失会回落到 owner 身份，只剩应用层过滤；行级安全也不防 SQL 注入。

### 20. 每次 `/chat` 的数据库往返从 167 降到 22，怎么定位的？

先测量再优化。压测报告里租户路径每个 `/chat` 的数据库往返多得反常，用 `pg_stat_statements` 按语句统计，定位到两个来源：run 存储每个 `/chat` 回读 26 次（事件列表 15、run 行 11）；每条租户语句单独一个 4 次往返的短事务（BEGIN、设置租户、语句、COMMIT）。改法：写入语句直接返回提交后的行和事件列表，请求内的 run cursor 只作 CAS 的乐观基准，冲突时照旧重读，不当缓存用；租户设置和语句用扩展协议流水线一次往返发出。结果：租户路径往返 167 → 22，owner 路径 46 → 20；并发 32 时租户 4 实例吞吐 205 → 283 req/s（+37.9%），单实例只 +12.6%，因为单进程受 CPU 限制；PostgreSQL 每请求 CPU 减半。审查找出并修掉两个问题：CAS 等锁期间并发追加的事件没出现在返回列表里，改为同一往返里先 `FOR NO KEY UPDATE`；流水线失败时可能把处于事务中的连接放回连接池。现在有测试把一次 `/chat` 的 run 存储语句数钉住，改它要附 `pg_stat_statements` 的实测。
