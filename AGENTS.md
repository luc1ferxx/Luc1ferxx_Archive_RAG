# AGENTS.md

## Project Shape

- Root app: React 18 / Vite frontend in `src/`.
- Backend: Node ESM Express API in `server/`, with custom RAG logic in `server/rag/`.
- Runtime/generated paths to avoid editing unless requested: `node_modules/`, `build/`, `server/node_modules/`, `server/data/`, `server/uploads/`, `server/upload-sessions/`, `server/evaluation/generated/`, and timestamped files under `server/evaluation/results/`.

## Setup

- Install frontend deps from the repo root: `npm install`.
- Install backend deps separately: `cd server && npm install`.
- The backend needs Node >= 22.13 (`server/package.json` engines; pdfjs-dist 6 uses `Promise.withResolvers`, missing on Node 20). CI runs Node 22, the image is `node:22-bookworm-slim`; local development has used Node 24.
- Copy `.env.example` for frontend settings and `server/.env.example` to `server/.env` for backend settings.
- Start the default retrieval backend with `docker compose up -d` from the repo root (PostgreSQL 16 with pgvector, healthcheck, persistent volume); `server/.env.example` already points `POSTGRES_DATABASE_URL` at it. Migrations run at startup and on health checks.
- Required backend keys for full RAG/web behavior: `OPENAI_API_KEY` and `SERPAPI_KEY`.
- One-click deployment: `docker compose --profile app up -d --build` builds the root `Dockerfile` (the API server also serves the built frontend through `FRONTEND_BUILD_DIRECTORY`, and the page calls the API on its own origin via `VITE_DOMAIN=same-origin`) and runs it next to PostgreSQL on http://localhost:5001; `--profile layout` adds docling-serve, `--profile shared-state` Redis, and `-f compose.rerank.yml --profile rerank` the cross-encoder reranker. See `docs/deployment.md`. The image installs server dependencies with `--legacy-peer-deps` because npm 10.9 insists on a TypeScript peer the npm 11 lock file leaves out; keep that flag or regenerate the lock with the image's npm.
- Compose network exposure: every published port (postgres 5432, redis 6379, app 5001, docling 5010, and `api` in `compose.services.yml`) binds `${ARCHIVE_RAG_BIND_HOST:-127.0.0.1}`, and `POSTGRES_PASSWORD` (default `postgres`, URL-safe characters only, applied only when the `pgdata` volume is first initialized) feeds the postgres service and every compose database URL. To open it on a network, set `POSTGRES_PASSWORD`, enable API auth, then start with `ARCHIVE_RAG_BIND_HOST=0.0.0.0` (or one interface address); it widens every port at once and Redis has no password. The app healthcheck probes `/ready`. `test/deployment-contract.test.mjs` pins all of this.

## Development Commands

- Run frontend and backend together from the repo root: `npm run dev`.
- Run only the frontend: `npm start`.
- Run only the backend: `npm run server` from the root, or `cd server && npm run start`.
- Monolith shutdown (`server.js`, role `all`): the first SIGTERM/SIGINT runs the split roles' `createGracefulShutdown` (`rag/agent-service/role-server.js`). It stops listening, lets in-flight requests (a `/chat`, an SSE stream, an upload) finish within `SERVICE_SHUTDOWN_GRACE_MS` (default 25 s), and stops the in-process ingest worker at the same time (`INGEST_WORKER_STOP_GRACE_MS`, 5 s, then running jobs go back to the queue). It then runs `app.locals.stop`, the span flush (`createTracingShutdownFinalizer` in `otel.js`; the monolith no longer registers `shutdownTracingOnExit`, which exits on the signal and would cut the drain), the metrics listener close and `resetPostgresPool`, and exits 0. A second signal exits 1 at once, and so does a shutdown still running after max(drain window, 5 s when a worker runs) + 3 s. The compose `app` service has `stop_grace_period: 30s` (pinned by `test/deployment-contract.test.mjs` against the default grace + 3 s); raise it together with `SERVICE_SHUTDOWN_GRACE_MS`. The drain covers HTTP requests only: background agent tasks in the process are still cut and left to startup recovery. `test/monolith-graceful-shutdown.test.mjs` runs `node server.js` as a child process.
- Default ports are frontend `3000` and backend `5001`; the backend also honors `PORT`.
- Run one tier of a split deployment: `cd server && ARCHIVE_RAG_ROLE=<api|agent|retrieval|model-gateway> node server.js`. Ports: `PORT`, else 5001 (api, agent), 5002 (retrieval), or `MODEL_GATEWAY_PORT`, then `PORT`, then 5003 (model-gateway). `node retrieval-service.mjs` and `node model-gateway.mjs` are the dedicated entry points of the last two. With the role unset the process is the monolith (`all`). `npm run start:api|start:agent|start:retrieval|start:model-gateway` wrap the same entry. `compose.services.yml` (an override of `docker-compose.yml`, not combinable with `--profile app`) runs the four tiers from one image with internal identity taken from the shell only (`INTERNAL_SERVICE_AUTH`, default `hmac` with `INTERNAL_SERVICE_KEYS`; under `ed25519` each calling tier gets its own `INTERNAL_SERVICE_SIGNING_KEY_API|_AGENT|_RETRIEVAL` plus the shared `INTERNAL_SERVICE_TRUSTED_KEYS`, printed by `eval "$(node server/service-keys.mjs compose)"`) and only api published. Missing keys are refused by topology validation when a container starts (it exits and `restart: unless-stopped` retries), not by compose interpolation. `test/deployment-contract.test.mjs` pins it, and it has only been checked with `docker compose config`, never built. `test/service-split.e2e.test.mjs` drives /chat and /chat/stream through all four tiers and compares with the monolith. See "Service split" below and `docs/deployment.md`.
- Build the frontend: `npm run build`.

That is safe because `test/run.test.mjs` and `test/coverage-gate.mjs` discover the same files (every `server/test/*.test.mjs` except `run.test.mjs`, sorted) and the gate exits non-zero when any test fails, so the workflow contract in `ci-workflow.test.mjs` is still checked. `ci-workflow.test.mjs` pins this: exactly one `coverage:gate`, no `npm test`, the timeout, and the two discovery functions (compared as whitespace-stripped source, so a change to either one must be made to both). The gate buffers the child's stdout until the end, so test output appears in the CI log only after the suite finishes (stderr is live). `quality-gate` runs the deterministic evals and `quality:current`.

Use `-- --no-fail` only for diagnostics; it does not change a failing report to pass.

- Ragas eval runs against saved Node eval payloads: `cd server && npm run eval:ragas -- --input evaluation/results/latest.json`. It requires optional dependencies plus `OPENAI_API_KEY`; see `server/evaluation/ragas-requirements.txt`.
- Retrieval arm comparison: `cd server && npm run eval:retrieval-comparison` uses the deterministic hashed-TF embedding (plumbing only, never an effect claim). `-- --embedding-provider openai` runs real embeddings against any OpenAI-compatible endpoint (including local Ollama) and writes `latest-retrieval-comparison-openai.*` so it never overwrites the deterministic report; `--rerank-provider cross-encoder --cross-encoder-endpoint <url>` measures a neural reranker. Every split reports paired bootstrap 95% CIs; do not describe an arm difference as better unless its interval excludes 0.
- LLM call resilience: `cd server && npm run eval:llm-resilience [-- --no-fallback]` injects 429 (precise and coarse Retry-After), 503s, hanging requests, empty completions, and a down primary against a local fake OpenAI server; no model or key needed.
- Prompt-injection red team: `cd server && npm run eval:prompt-injection` (real model required; cases in `evaluation/prompt-injection-cases.js`) measures attack success on the document RAG answer that MCP `archive_ask` returns and on the `/chat` agent path, plus claim-judge false accepts under a checker-directed payload; `--only` runs selected cases. It writes ignored `evaluation/results/latest-prompt-injection*.{json,md}`.
- Tenant isolation eval: `cd server && npm run eval:tenant-isolation` provisions its own throwaway database (the `PGVECTOR_TEST_DATABASE_URL` login needs CREATEROLE and CREATEDB), seeds 20 tenants, and compares `POSTGRES_ROW_LEVEL_SECURITY=off` (the pre-RLS connection path) with `enforce` on cross-tenant reads/writes, latency, and query plans; it writes ignored `evaluation/results/latest-tenant-isolation.*`.
- QASPER: `npm run corpus:qasper -- --input <qasper-dev-v0.3.json> --papers all` converts a QASPER release (downloaded to the ignored `evaluation/generated/qasper/`) into the corpus format with paragraph-level evidence pages by default (`--granularity section` is coarser and inflates recall) and every annotator's answer in `referenceAnswers`; `test/qasper.test.mjs` covers it. Run retrieval on it with `npm run eval:retrieval-comparison -- --embedding-provider openai --corpus evaluation/generated/qasper-dev.json --splits full --no-refusal` (the tuning/held-out splits are defined for the arXiv corpus only), and answers with `npm run eval:qasper-answers [-- --cases 200 --surface rag|agent]`, which scores the official QASPER answer F1 (no LLM judge) plus abstention and two evidence figures that must not be confused. Cited: `citedEvidenceRecall` (an annotated evidence page among the pages the answer's `[Source N]` labels resolve to through `citedSourcePages` in `evaluation/qasper-answer-metrics.js`; an abstention cites nothing), `citationPrecision` (macro mean of evidence pages over distinct cited pages, answered answerable rows that cite a page, `citationPrecisionCases`), and `noCitationRateWhenAnswered`. Context: `contextEvidenceRecall` (an evidence page among the pages the model was shown, cited or not; the QA path returns every context chunk as a citation, so it is not a citation metric). Reports before 2026-10-04 called the context figure `evidenceRecall` and the row field `evidenceHit`; pair an old `evidenceHit` only with a new `contextEvidenceHit`. Recall figures also come as `...WhenAnswered`. The runner prints no CIs; compute paired bootstrap CIs from the per-row fields. Token F1 punishes long answers; compare this system's runs with each other, not with span-extraction leaderboards.
- Abstention gate analysis: `cd server && npm run eval:abstention-gate -- --corpus evaluation/generated/qasper-train.json` retrieves each QASPER question once through `retrieveQaCandidates` (exported from `rag/document-rag-execution.js`, the QA route up to its gate) and replays the real `assessQaConfidence` over a threshold grid without a chat model. Single-document QA reads `RAG_MIN_QA_QUERY_TERM_COVERAGE` and comparison reads `RAG_MIN_QUERY_TERM_COVERAGE`; both default to 0.51. Do not lower the QA default: every value at or below 0.5 flips the adjacent-topic behaviour tests in `test/rag.test.mjs` and `test/rag-boundary-coverage.test.mjs`, and 0.2 lowered QASPER dev answer F1 from 0.206 to 0.153 (paired CI excludes 0). The report's second row is the gate with `RAG_QA_ANSWER_VERDICT` on (partial band plus substitution veto), before the model's verdict, which the analysis does not call; `eval:qasper-answers` rows record `abstainSource` (`gate` or `answer_model`).
- QASPER evidence recall: `cd server && npm run eval:qasper-retrieval -- --corpus evaluation/generated/qasper-train.json --cases 400 [--compare <other report.json>]` retrieves each answerable question once through `retrieveQaCandidates` and records per question whether an annotated evidence paragraph is at rank 1, in the top 3, among all candidates, and among the chunks the default gate admits; `--compare` adds paired bootstrap CIs against another run over the same sample. No chat model. Tune on train, confirm on dev.
- Layout parsing: `cd server && npm run eval:layout-parsing` parses the QASPER dev papers with the most table-evidence questions (PDFs from arxiv.org, downloaded beforehand into the ignored `evaluation/generated/qasper-pdfs/`) with both pdf.js and Docling, ingests both side by side, and asks every answerable question of both versions: whether a gold extractive span occurs in the parsed text and in the retrieved chunks, and the official answer F1, with paired CIs; text-evidence questions of the same papers are the control. Needs docling-serve (`DOCLING_SERVE_URL`) and a real model. `-- --parsers pdfjs,pdfjs-paragraphs` compares legacy pdf.js with pdf.js under `PDF_PARAGRAPH_DETECTION` instead (no docling-serve; the delta is the second parser minus the first, and the report adds an all-questions section); `--concurrency N` keeps N questions in flight.
- Real-model CI: `.github/workflows/real-model-eval.yml` (weekly and manual) installs Ollama on the runner with `nomic-embed-text` and a chat model (default `qwen2.5:7b`), no API key, then runs `verify:quality` (blocking), `eval:qasper-retrieval` on a fixed 200-question QASPER dev sample with `--min-hit-at-all 0.6` (blocking; 0.655 when set), and a small `eval:qasper-answers` sample (report only); `test/ci-workflow.test.mjs` pins that contract.
- Load test: `cd server && npm run eval:load-test:pgvector` (or `eval:load-test` for the local store only) runs `evaluation/run-api-load-bench.mjs`. It starts the real app from `createApp()` in a child process against an in-process fake OpenAI-compatible model with injected chat latency (0 and 800 ms by default), then drives closed-loop `/chat` and `GET /documents` load at concurrency 1/4/16/32. The wrapper creates a disposable Postgres.app cluster on an OS-assigned port and removes it on exit. The runner never reads `server/.env`, and it refuses a `--database-url` that already has `schema_migrations`. Keep the file name off Node's `*-test.mjs` glob, or coverage drops it. It writes ignored `evaluation/results/latest-load-test.*`. With a PostgreSQL registry, `GET /documents` and the start of every `/chat` re-read the tenant's document rows (cross-instance visibility), so the old in-memory `GET /documents` figure no longer applies. Multi-instance and ingest options: `--instances`, `--balance` (default least-outstanding), `--shared-state redis`, `--tenant` (tenant transactions under RLS; without it the report says owner path), `--no-analyze`, `--scenario ingest`, `--ingest-mode`, `--ingest-workers`, `--repeat`; keep both sides of any before/after pair under their own `--latest-name`. `--topology split` (`npm run eval:load-test:split`) runs each tier as its own child process (`--api/--agent/--retrieval/--gateway N`, chat scenario and pgvector only), with the fake model behind the gateway, and reports per-tier CPU, the busiest tier and `model.directCalls` (must be 0). `--repeat N` now also applies to chat and reports min-max ranges. The model concurrency cap is per gateway process in split mode and per instance in monolith mode unless `--with-redis`, so compare 800 ms figures across topologies with that in mind. `bash scripts/run-load-test-pgvector.sh --read-replica --tenant [flags]` also provisions one streaming replica of the disposable primary (pg_basebackup -R, OS-assigned port), loads pg_stat_statements on both nodes and passes `--read-replica-url`, which sets `POSTGRES_READ_REPLICA_URLS` for the app processes (it needs `--tenant` and pgvector). The report adds `config.readReplica` and per run `readReplica` (routing counts over the measured chat levels, and per-node statement counts by kind); `test/postgres-replica-load-bench.test.mjs` covers those helpers. The replica runs on the same machine as the primary, so the report says nothing about network distance.
- Read-replica integration: `cd server && bash scripts/run-pgvector-replica-integration.sh` provisions a disposable primary (`wal_level=replica`) and a `pg_basebackup -R` hot standby on OS-assigned 127.0.0.1 ports under `$TMPDIR`, runs `test/postgres-replica.integration.test.mjs` with `PGVECTOR_TEST_DATABASE_URL` and `PGVECTOR_TEST_REPLICA_URL` (superuser, because it pauses replay with `pg_wal_replay_pause`), and removes both on exit (`KEEP_CLUSTER=1`, `PG_BIN_DIR`, `PGVTEST_DB` optional). Without both URLs the suite is skipped. It is not part of `test:pgvector` or CI, and there is no npm script for it yet.
- pgvector scale: `cd server && npm run bench:pgvector-scale` loads 10k–1M synthetic chunks into a disposable cluster through the real migrations. It times the app's dense, sparse and hybrid searches under RLS enforce, with warm series and separately timed first reads, and measures recall@10 against the exact result of the app's own SQL. Filtered series check every query, and the report states whether HNSW was used. It writes ignored `evaluation/results/latest-pgvector-scale.*`. A recall of 1 from a plan that did not use HNSW says nothing about the index. The whole-table HNSW recall on this synthetic data is a stress case, not an app path.
- Framework-only entry point (not yet run on real data): `npm run eval:judge -- --input <answers.json> [--labels <labels.json>]` is an LLM judge that reports agreement and Cohen's kappa against human labels. Do not quote judge scores that have not been calibrated.

## Implementation Notes

- Keep RAG changes inside `server/rag/` where possible; route/API behavior lives in `server/app.js`.
- AgentRAG skills are registered in `server/rag/skills/registry.js`; built-ins live in `server/rag/skills/built-ins.js`, and whitelisted custom skills live under `server/rag/skills/custom/`. Current custom skills include `extract_timeline`, `risk_review`, `summarize_contract`, and `compare_documents`.
- New skills need stable `id/version/label/budgetKey/requiresAccessScope`, deterministic `match()`, and an `execute()` path that receives `accessScope` when reading user/workspace data. Custom skills must be exported from `server/rag/skills/custom/index.js`; do not let the model call arbitrary unregistered tools. The model-facing atomic custom-Skill catalog in `server/rag/skills/authorized-catalog.js` is narrower: it requires explicit typed input/output contracts, declared effects, a scoped document input, and successful `getDocument(docId, accessScope)` checks for every selected document; an empty or unverifiable document set grants no catalog entries. It is independent of V1 intent `match()` and composite chains.
- Agent bootstrap/session setup lives in `server/rag/agent-bootstrap.js`; keep working memory creation, planning, selected skill ordering, run context creation, and skill tracker wiring there.
- Agent preparation flow lives in `server/rag/agent-preparation-flow.js`; keep plan trace, pre-execution clarification, query planning trace, and skill chain trace there.
- Agent run context lives in `server/rag/agent-run-context.js`; keep trace appending, budget snapshot helpers, agent trace recording, observability assembly, and clarification response orchestration there rather than rebuilding those cross-cutting helpers in `server/rag/agent.js`.
- Document RAG execution loop lives in `server/rag/agent-document-loop.js`; keep primary document RAG, self-check, gap analysis, follow-up retrieval, evidence clarification, and working-memory claim/gap updates there rather than expanding `server/rag/agent.js`.
- Non-document skill execution is exported through `server/rag/agent-skill-runners.js`; built-in runners live in `server/rag/agent-built-in-skill-runners.js`, custom skill chain execution lives in `server/rag/agent-custom-skill-runner.js`, and web search execution lives in `server/rag/agent-web-runner.js`. Keep those execution details out of `server/rag/agent.js`.
- The custom skill stage has two execution paths behind one seam. `server/rag/agent-custom-skill-stage.js` resolves `AGENT_SKILL_GRAPH_ROLLOUT` (`guarded` / `shadow` / `off`, default `guarded`; an unrecognized value resolves to `off`) and either runs the V1 sequential chain in `agent-custom-skill-runner.js` or the V2 typed DAG. Both paths return the same flat skill result array, emit the same `custom_skill` step type, and share one run store and one replay safety matrix; do not stand up a parallel runtime or a second run store. `guarded` falls back to V1 only when a graph is rejected before any node ran — there is deliberately no fallback after partial execution. The executor dial and the planner dial are separate: the DAG planner follows `AGENT_EXECUTION_PLANNER` and a failed LLM plan falls back to the deterministic graph rather than straight to the V1 chain, so `rollout:readiness` (zero fallback, zero mock/real divergence) measures pure-LLM planning and is not the gate for the executor default. Under `guarded` the LLM execution planner sees authorized atomic Skills and may add a `custom_skills` stage the intent did not select. Keep the V1 chain (whole-graph-rejection fallback and the `off` opt-out), the composite intents, and the deterministic planner.
- The V2 typed DAG is split across `server/rag/agent-execution-graph.js` (versioned graph contract plus the pure-function validator/compiler), `agent-execution-graph-runner.js` (stable topological scheduler, runtime concurrency cap, atomic budget reservation, side-effect serialization, node run records, and runtime input/output schema gates), `agent-dag-planner-adapter.js` (redacted whitelist-only planning surface that emits atomic skill nodes rather than composite chain ids), and `agent-replanner.js` (bounded patch-only replan, `maxReplans: 1`). Every initial plan and every replan patch goes through the same validator, which accepts or rejects a graph whole so an illegal graph never partially executes. The runner also validates resolved input before budget/execution and actual output before downstream binding, including reused checkpoint output. Node inputs bind only to validated request fields or upstream node outputs; do not reintroduce concatenated free text as the primary data interface. The planner never decides scope, `docIds`, approvals, budget, concurrency, or retry limits — the runtime owns those. This DAG covers custom Skills only, not the outer document/web/built-in/capability stages.
- The heterogeneous v3 unified graph has a scoped unfreeze (decision and remaining freeze in `docs/unified-agent-dag-migration.md`).
  - **Rollout:** `AGENT_UNIFIED_GRAPH_ROLLOUT` is `off` (default), `shadow`, or `guarded`; any unrecognized value resolves to `off`. `shadow` is unchanged: it validates a proposal and records a redacted `unified_graph_planned` event without executing it.
  - **Guarded path:** `agent-unified-graph-run.js` handles `/chat` and background tasks. Planning is `agent-unified-dag-planner.js` with an injected `unifiedGraphPlannerAdapter`; there is still no default model adapter. Admission (`agent-unified-graph-admission.js`) and validation happen before anything is persisted.
  - **Fallback before execution:** a refused graph is recorded in a `unified_graph_planned` event with `status: "rejected"` and `fallback: "v1"`, plus a `unified_graph_fallback` trace step, and V1 answers the request unchanged. Refusal reasons are: no planner, an invalid proposal, an approval-gated node (a Capability adapter with an approval gate, or a Web/discovery built-in without a standing, input-independent grant in `capabilityApprovals`), or a shape the legacy finalizer cannot represent (`describeUnifiedGraphProjectionShape`).
  - **Re-entry:** a run re-entered through `agentRunId` always stays on V1 (`approval_continuation_frozen`). Graph approval continuation remains frozen; do not wire it without new cross-process approval recovery evidence.
  - **After admission:** once admitted, the request runs only on the graph path (`status: "selected"` event, no `execution_planned` event) and never falls back to V1. It uses the same run store, validator/scheduler, budget reservation, replay matrix, and fenced graph lifecycle.
  - **Finalization:** results are projected by `projectUnifiedGraphRun` (primary document plus at most one follow-up conditioned on the primary check's `retryRecommended`, one Web node, custom Skills). `agent-unified-graph-document-loop.js` rebuilds document-loop claims, gaps, and loop counters from persisted typed outputs. The same `finalizeAgentRun` then finalizes the answer.
  - **Finalization receipt:** the finalized response is sealed as a `finalization` receipt in the private v2 checkpoint before the run completes.
  - **Startup recovery:** it routes a v2 checkpoint to the dedicated v3 continuation only when the run's events prove the guarded path (`hasUnifiedGuardedGraphPath`). It may claim a v2 checkpoint that is `running` or `completed`. It completes the run from the receipt, or replays a completed graph without executing any node. It reuses only nodes whose typed-output digests reconcile. Unknown in-flight work and tampered receipts are marked manual. A resumed run that settles as a clarification counts as settled, and a run already finalized as a clarification is skipped.
  - **Evidence:** the trajectory case `unified_graph_evidence_gated_skill_hand_off` (manifest 1.13.0) pins the orchestration V1 cannot express. - Structured chunker (`chunkPageWithStructure` in `server/rag/chunker.js`) never drops text. - Tenant statement round trips: A tenant-scoped `queryPostgres` sends the tenant settings and the statement as one extended-protocol pipeline: Parse/Bind/Execute for each, then a single Sync, so the whole thing is one round trip. The implicit transaction ends at the Sync, so the settings stay transaction-local, a failure rolls back, and the connection goes back to the pool as the owner. Under a tenant, `withPostgresTransaction` sends BEGIN plus the settings as one round trip, then the callback's statements, then COMMIT. The role and ids are always bind parameters, never SQL text, so do not build them into SQL with escapeLiteral. If a tenant statement leaves a transaction block open (for example a statement text of BEGIN), the call fails with `ARCHIVE_RAG_TENANT_PIPELINE_STATUS` and the connection is destroyed instead of pooled. A connection whose ROLLBACK failed is also destroyed. Tenant statements always use the extended protocol, so one call cannot carry several semicolon-separated statements. The pipeline relies on pg's Submittable interface (`PipelinedQuery` in `rag/postgres.js`). When pg is upgraded, run `test/postgres-tenant-pipeline.test.mjs` (a fake server that pins the exact wire messages) and the RLS integration suite. The native pg bindings fall back to the four-round-trip path. Like `pool.query` on the owner path, a tenant statement commits at the Sync: a client-side error (a `query_timeout`, a disconnect after the Sync) leaves the outcome unknown rather than rolled back, so a write that must not commit after a client error belongs in `withPostgresTransaction`.
- Read replicas (`server/rag/postgres-replicas.js`, `POSTGRES_READ_REPLICA_URLS`, unset by default; unset changes nothing, including the pinned statement counts).
  - **What may go to a replica:** only `queryPostgres(text, values, { readOnly })` with `readOnly` = `true` or `{ guard }`, under an enforced database tenant, outside `withPostgresTransaction` (`canRouteReadToReplica()`). The replica gets one pipelined round trip: tenant settings, the guard (as the tenant), an optional prelude, the statement, one Sync, so row-level security there is the primary's replayed policy. The only callers that mark reads are the pgvector dense search (plain and iterative; the iterative `set_config` becomes the prelude instead of a BEGIN/COMMIT) and the sparse search (BM25 / pruning function, tenant `ts_rank_cd` function, plain statement) in `vector-store-pgvector.js`, and only when no caller client is passed and every searched docId is in this process's registry map.

Those reads are the read-your-writes anchors or have none; do not mark them `readOnly`.
  - **Consistency:** `buildDocumentFreshnessGuard` makes the replica prove, in the search's own round trip, that it holds each searched document at least at the `content_version` the registry read from the primary and the index pointer at least at the generation of the snapshot the search's version came from (taken before any await; another snapshot keeps the search on the primary). A failing guard raises SQLSTATE 22P02 with `archive_rag_replica_behind`, the primary answers, and the read counts as `version_behind`. The anchors: `buildChatResponse` refreshes the tenant's registry rows from the primary before the run (when that refresh fails, `refreshDocumentsIngestedElsewhere` returns false and the whole run goes through `runWithPrimaryReads`, counted as the bypass `registry_unverified`, because a registry that missed a replace or delete would let a lagging replica pass the guard), and the retrieval tier's `maskInvisibleDocIds` re-reads every requested docId from the primary when routing is on. This relies on pgvector writes, replaces and deletes committing the document row with its chunks.
  - **Lag guard:** a monitor samples the primary's `pg_current_wal_flush_lsn()` every `POSTGRES_READ_REPLICA_LAG_POLL_MS` and each replica's `pg_last_wal_replay_lsn()`; lag is the age of the newest primary sample the replica has replayed past (unknown means skipped; an LSN that moves back restarts sampling). `pg_last_xact_replay_timestamp()` is not used. Replicas over `POSTGRES_READ_REPLICA_MAX_LAG_MS` (default 2000), unreachable, not in recovery, with an open circuit, or with `POSTGRES_READ_REPLICA_POOL_MAX` reads in flight are skipped. Choice is least in flight, ties rotate; each replica has its own circuit (`_CIRCUIT_FAILURE_THRESHOLD` 3, `_CIRCUIT_COOLDOWN_MS` 5000; only unavailable errors count).
  - **Fallback:** every replica error falls back to the primary and is counted (`version_behind`, `lag_exceeded`, `lag_unknown`, `circuit_open`, `replica_down`, `replica_saturated`, `replica_unavailable`, `recovery_conflict`, `replica_error`); a replica never fails a request. An invalid `POSTGRES_READ_REPLICA_URLS` (including one that names no URL, such as `,`) or an invalid integer setting makes every `readOnly` statement throw and `checks.readReplicas` report `error`: fail closed, never a silent fallback.
  - **Observability:** `getReplicaRoutingSnapshot()` (reads, fallbacks, bypasses, per-replica state, lag, circuit; endpoints are host:port, never a URL) feeds `metrics-postgres.js`. `checks.readReplicas` appears only when the variable is set and the process hosts the retrieval tier; it is `ok` or `warning`, never `error` for lag or a down replica, so `/ready` stays 200.
  - **Limits:** replica statements have only a connect timeout (`POSTGRES_READ_REPLICA_CONNECT_TIMEOUT_MS`), not the request deadline; BM25 on a replica uses that replica's scope statistics, which may predate other writes of the same tenant within the lag bound; `vector:reindex --apply` rewrites chunks without bumping `content_version`, so a lagging replica can miss re-embedded rows until it catches up; a failed registry refresh at the start of `/chat` is only logged, so the guard can be stale for that request; nothing checks that a replica follows this primary (`system_identifier`); the lag bound assumes `synchronous_commit` is on.

- The pgvector sparse route has two scorings. Set them with `RAG_SPARSE_SCORING=ts_rank_cd|bm25`; the default is `bm25`, and an unknown value throws.
  - `ts_rank_cd` is PostgreSQL's cover-density rank. Never call it BM25. Its runtime `sparseBackend` is `postgres_fts_ts_rank_cd`.
  - `bm25` is Okapi BM25 (`rag/vector-store-pgvector-sparse.js`, migrations 029/030). Its `sparseBackend` is `postgres_bm25`.

- Migration 030 installs `<chunks>_install_bm25(table, regconfig)`. It runs for the migration-012 table and for every live version table, and `createIndexVersion` calls it for each new version. It creates, per version table:
  - `sparse_length`: a BEFORE row trigger fills it with the tsvector position count. Rows written before 029 keep NULL and are counted at query time. Do not backfill with an UPDATE: that rewrites every HNSW entry.
  - `<t>_sparse_scopes` and `<t>_sparse_terms`: statistics keyed by (owner_user_id, workspace_id), with a tenant GRANT and the `tenant_isolation` policy.
  - statement-level INSERT/UPDATE/DELETE/TRUNCATE triggers with transition tables. They keep the statistics exact for every writer, cascades and bulk loads included.
  - `<t>_bm25_rank(...)`, which is SECURITY DEFINER.
- Retire drops these objects after the table (`renderPgvectorBm25DropDdl`).
- Trigger lock order: scope rows first (sorted with COLLATE "C"), then lexeme rows (sorted). The scope row is the per-scope lock and is held to commit. Do not add a writer that touches statistics rows before chunk rows.
- The rank function:
  - takes the scopes of the searched documents from the documents table, so one tenant's statistics never reach another tenant;
  - under the tenant role, filters the doc ids with the policy predicate itself, so a direct call with another tenant's ids returns nothing;
  - has one statement for every caller.
- Common-term pruning (`RAG_BM25_PRUNE_DF_FRACTION`, default 0.1):
  - candidates come through GIN from terms whose document frequency is at most that share of the scope's chunks, and every term then scores them;
  - it runs exhaustively when pruning would keep no terms or all of them, when the documents hold at most `PGVECTOR_BM25_PRUNE_MIN_CHUNKS` (1000) chunks, or when fewer than K candidates come back.
- `npm run eval:sparse-scoring` measures this route. `eval:qasper-retrieval` measures the local store instead. `bench:pgvector-scale -- --sparse-doc-sets ... --prune-df-fractions ...` measures latency.

A URL moves that work to the tier in every role except the tier's own (a tier never calls itself), so one environment can be handed to every role. The getters throw on a bad value; never add a silent fallback to in-process work. `hostsServiceTier("agent")` decides whether a process runs agent recovery and background agent work. Role `agent` without `RETRIEVAL_SERVICE_URL` retrieves in process (a warning, not an error).
  - **Internal identity** (`rag/service-identity.js`, `rag/service-identity-keys.js`): a short-lived token in `x-archive-service-token`, audience = target tier, issuer = the caller's role (`getServiceIssuer`; a role-`all` process may sign as `ingest-worker` with `INTERNAL_SERVICE_ISSUER=ingest-worker`). `INTERNAL_SERVICE_AUTH` picks the scheme; any other value refuses the start and every sign/verify:
    - `hmac` (default): HS256 with the shared `INTERNAL_SERVICE_KEYS`, first key signs, every key verifies. Rotate in three rolling restarts: append the new key (verify only), move it to the front (it signs), then remove the old one; prepending it in the first round makes restarted tiers sign with a key the others do not know yet. Every tier holds every key, so under `hmac` the issuer is self-asserted.
    - `ed25519`: EdDSA with this process's own `INTERNAL_SERVICE_SIGNING_KEY` (PKCS8 PEM or base64 DER; kid `INTERNAL_SERVICE_SIGNING_KEY_ID`, default a fingerprint of the public key), verified with `INTERNAL_SERVICE_TRUSTED_KEYS` (`issuer:kid:base64spki,...`). A public key speaks only for the issuer it is registered under (`SERVICE_TOKEN_KEY_ISSUER` otherwise), so a compromised tier can sign only as itself. HS256 tokens are refused. The model gateway calls nobody and needs no signing key.
    - `mixed`: signs EdDSA and accepts both, for the rolling move. Order (header of `service-identity-keys.js`): every tier to `mixed`, callees first (model-gateway, retrieval, agent, api), then every tier to `ed25519` in any order, then drop `INTERNAL_SERVICE_KEYS`. Rotate an Ed25519 key in three rolls: append its new public entry everywhere, switch that tier's signing key, remove the old entry after the token lifetime.
    - The algorithm is pinned per key (no HS256/EdDSA confusion); signatures must be canonical 64-byte base64url; `timingSafeEqual`, expiry and clock-skew checks stay.
    - **Call policy:** `SERVICE_CALL_POLICY` in `service-identity.js` is the one table, enforced at the receiver in every mode (also under `hmac`): agent ← `all`, `api`; retrieval ← `agent`, `all` (probe also `api`); model-gateway ← `agent`, `all`, `api`, `ingest-worker`, `retrieval`. `requireServiceIdentity`'s `issuers` can only narrow it, and an unknown audience throws.
    - **Request binding:** the service client signs a fresh token per attempt with `htm` (method), `htu` (SHA-256 of path and query; the query may hold a question) and `bdh` (SHA-256 of a non-empty body). The receiver checks method and target in `requireServiceIdentity` and the body in `express.json({ verify: verifyServiceRequestBody })` + `handleServiceRequestBodyError`; a token with `bdh` is accepted only with `application/json`. Required for EdDSA tokens, checked when present on HS256 ones (`INTERNAL_SERVICE_REQUEST_BINDING=required|optional` overrides). A new internal receiver must mount the verify hook, or only method and target are bound. A proxy that rewrites the internal target or body breaks calls in every mode.
    - **Replay cache** (`rag/service-token-replay.js`): each token id is accepted once until it expires. On by default under `ed25519` and `mixed`, off under `hmac` (`INTERNAL_SERVICE_REPLAY_CACHE`). Per process and bounded (`INTERNAL_SERVICE_REPLAY_CACHE_MAX_ENTRIES`, default 100000; past it the oldest entries are evicted, which reopens their window); with `RAG_SHARED_STATE=redis` shared across replicas through `SET NX PX`, falling back to the local verdict on a Redis error. Under `hmac` without it, tokens remain bearer tokens for their TTL.

The retrieval tier runs each request inside `runWithServiceCallDeadline` and the agent tier mounts `bindServiceCallDeadline` (`call-deadline.js`, after `requireServiceIdentity`): outbound calls spend at most what is left of the inbound deadline, and in-flight model calls are aborted when it passes; database statements are not cancelled. A caller that disconnects early does not stop the retrieval tier's work before its own deadline.
  - **Never in role `api`:** `runAgentRag`, agent startup recovery, `recoverRunnableTasks`, task execution, admin actions (they are forwarded). Each role reports only its tiers' health checks (`HEALTH_CHECKS_BY_TIER` in `health.js`); split processes add `checks.serviceTopology`, and the edge adds `checks.agentService`, which is a warning and never an error, so `/ready` stays 200 while the agent tier is down.
  - **Invariants:**
    - A route added to `routes/chat.js` or `routes/tasks.js` must be added to `AGENT_EDGE_ROUTES`, with `idempotent: false` if it is a GET that writes; a test fails otherwise.
    - A new model call goes through `openai.js` or `reranker.js`, so gateway mode covers it. `chat-mcp.js` requires a local `OPENAI_API_KEY` only when the model gateway is off.
    - Nothing that crosses a tier (error bodies, log lines, span attributes, token claims) carries a question, prompt, model output, document text or secret.
    - Every split role shares one PostgreSQL for documents, runs, tasks, audit and ingest jobs; memory-backed stores do not work across tiers, and the topology check does not detect that.
    - A new internal receiver mounts `requireServiceIdentity` with an audience from `SERVICE_CALL_POLICY` and `express.json({ verify: verifyServiceRequestBody })` + `handleServiceRequestBodyError`. A new agent route that runs a run goes through `runAgentRequestWithCancellation`, and new long work checks `throwIfRequestCancelled` at a boundary, never in the middle of an effect.
  - **Tests:** `service-topology`, `service-identity`, `service-client`, `service-roles` (edge and agent tier), `service-roles-server` (start-up, shutdown, health per role), `service-roles-tracing` (one trace across the edge hop), `model-gateway`, `model-gateway-units`, `retrieval-service` (parity, masking, bounds, failover, deadline, usage), `retrieval-service-process`, `retrieval-service-remote-only`, `retrieval-service-tracing`, all under `server/test/*.test.mjs`. `retrieval-service-pgvector.integration.test.mjs` needs `PGVECTOR_TEST_DATABASE_URL` and is reported as skipped without it. Identity: `service-identity-ed25519` (keys, modes, algorithm pinning, issuer binding), `service-identity-binding` (htm/htu/bdh, content type, replay cache; its real-Redis case needs `REDIS_TEST_URL` and is skipped without it), `service-identity-processes` (cross-process gateway hop), `service-identity-split` (api → agent → retrieval → gateway as four processes under `ed25519` with binding required and the replay cache on; retrieval uses the local store there, not PostgreSQL), `service-identity-tool` (`service-keys.mjs`). The older `service-roles`, `service-roles-server`, `retrieval-service` and `model-gateway` suites hand-sign unbound tokens and assume `hmac`; they do not pass under `INTERNAL_SERVICE_AUTH=ed25519`.
- Deadlines, cancellation and dependency outages (`server/rag/request-deadline.js`, `server/rag/dependency-outage.js`; monolith and split alike).
  - **Where the deadline comes from:** `/chat`, `/chat/stream` (GET and POST) and `POST /agent-runs/:runId/actions/:action` run under `runAgentRequestWithCancellation`. The deadline is the earlier of the inbound service deadline (`x-archive-service-deadline-ms`, which the edge sets from `AGENT_SERVICE_TIMEOUT_MS`) and arrival + `AGENT_REQUEST_TIMEOUT_MS` (default `0` = none; very large values are timed in steps, not cut at the 2^31 ms `setTimeout` limit). `AGENT_CANCEL_ON_DISCONNECT=on` (default off) also cancels when the client disconnects, including before the route bound the request. With neither, the monolith binds nothing and behaves as before; a split agent tier always has the edge's deadline.
  - **What is cancelled:** outbound calls in a bound request spend `min(own timeout, remaining)` and carry the request signal (remote retrieval, model-gateway client post and stream, direct `openai.js` chat/embeddings with abortable backoff and no retry after an abort, `reranker.js`, `chat-mcp.js` web search; a custom provider's `completeText` gets `options.signal`, its `embedTexts`/`embedQuery` do not). The run stops at safe points only: each execution-plan stage, `startStep`/`startGraphStep`, each graph node launch, `executeAgentSkill` entry (which rethrows the cancellation instead of returning a failed Skill result), and before `finalizeAgentRun`. A Capability with `approvalPolicy.writesWorkspace === true` runs outside the request store once started: it completes, its step completes, and the run stops at the next safe point; the effect is kept and never replayed. Database statements never read the signal. Scheduled tasks run under `runOutsideRequestDeadline`, so they never inherit a request's deadline or signal.
  - **Terminal states:** through the existing revision-CAS `failRun`: deadline → `failed` with `run.error.code` `AGENT_DEADLINE_EXCEEDED`, `reason: deadline_exceeded`, `retryable: true`; client gone → `canceled` (`run_canceled` event with `{error, reason, status}`), `AGENT_CLIENT_CANCELLED`, `retryable: false`; outage → `failed` with `retryable: true`, `dependency` and `causeCode`. Once a `capability_call` step has completed, `failRun` records `retryable: false` instead and the answer drops `Retry-After` and says `retryable: false` (agent-runs.js `hasCommittedCapabilityWrite`): a retry would repeat the write. Other errors keep `{message, name}`. A cancelled v3 approval continuation now fails the run instead of `markManualRecovery`. Startup recovery never lists failed or canceled runs.
  - **Answers:** deadline → 504 `{code: AGENT_DEADLINE_EXCEEDED, reason, retryable: true, agentRunId?}` without Retry-After; client gone → 499. A dependency outage (codes and statuses only: `SERVICE_UNREACHABLE|UNAVAILABLE|TIMEOUT`, `MODEL_GATEWAY_*`, `MODEL_UPSTREAM_*`, `CIRCUIT_OPEN`, the retrieval tier's restored 502/503/504, a direct model 5xx/408 or network error, PostgreSQL 08xxx/57P01-03/53300 or a lost connection; never a 4xx, 429 or protocol error) → 503 `AGENT_DEPENDENCY_UNAVAILABLE` (504 `AGENT_DEPENDENCY_TIMEOUT`) with `Retry-After` (the cause's, else 5) and `{code, error (generic), dependency, causeCode?, retryAfterSeconds, retryable: true, agentRunId?}`. SSE ends with `error` (`{...same body, status}`) and `done`, no `result`; a completed run keeps `result` identical to `/chat`. Helpers: `describeAgentRouteError` / `sendAgentRouteError` in `routes/chat.js`.
  - **Behaviour that changed by default:** a failed primary `document_rag` step (V1 loop) or v3 primary node, a `custom_skills` stage whose every result failed on an outage, a research brief whose every question failed on an outage, or an outage thrown anywhere in the run or in `buildChatResponse` now answers 503/504 and fails the run. It used to fall through to the Web stage and answer 200 with a Web-approval clarification. Ordinary evidence gaps keep their 200 clarification; non-outage errors keep `{ error: message }` and their status. Background tasks with an outage now fail instead of pausing for Web approval. `service-split.e2e` asserts the new 503 for a stopped gateway or retrieval tier.
  - **Circuit breaker:** a model call its own caller cancelled (a `RequestCancelledError`, directly or as a cause) is neither a failure nor a success for `model-call-guard.js`; a cancelled half-open probe gives its turn back (`breaker.abandon()`). Counting deadline aborts as failures let five short deadlines open the circuit for every tenant of the process (measured: 226 of 234 runs answered 503 instead of 504).
  - **Limits:** a writing Capability that crosses the deadline completes and the run then fails as not retryable (above); v3 completes the same run (no safe point after the last node). The model-call guard's concurrency queue does not observe the signal. The retrieval tier does not stop when its caller disconnects. A v3 non-primary node (follow-up, Web, custom Skill) that hits an outage still ends 409 `AGENT_UNIFIED_GRAPH_PARTIAL`, and an outage during a v3 approval continuation still goes to manual recovery. A direct-model connection failure is labelled `dependency: "dependency"`, not `model`. An agent replica answering an outage 503 is still marked unhealthy at the edge for the cooldown.
  - **Tests:** `request-deadline` (store, budgets, timers, disconnect before binding), `agent-cancellation` (safe points, terminal states, writing Capability, v3 approval continuation, outage answers), `request-deadline-split` (real edge and agent apps over HTTP with stand-in retrieval and gateway), all `server/test/*.test.mjs`. Split-mode disconnect cancellation and a real retrieval tier aborting at its deadline are not tested end to end.
