# AGENTS.md

## Project Shape

- Root app: React 18 / Vite frontend in `src/`.
- Backend: Node ESM Express API in `server/`, with custom RAG logic in `server/rag/`.
- Runtime/generated paths to avoid editing unless requested: `node_modules/`, `build/`, `server/node_modules/`, `server/data/`, `server/uploads/`, `server/upload-sessions/`, `server/evaluation/generated/`, and timestamped files under `server/evaluation/results/`.

## Setup

- Install frontend deps from the repo root: `npm install`.
- Install backend deps separately: `cd server && npm install`.
- Copy `.env.example` for frontend settings and `server/.env.example` to `server/.env` for backend settings.
- Start the default retrieval backend with `docker compose up -d` from the repo root (PostgreSQL 16 with pgvector, healthcheck, persistent volume); `server/.env.example` already points `POSTGRES_DATABASE_URL` at it. Migrations run at startup and on health checks.
- Required backend keys for full RAG/web behavior: `OPENAI_API_KEY` and `SERPAPI_KEY`.

## Development Commands

- Run frontend and backend together from the repo root: `npm run dev`.
- Run only the frontend: `npm start`.
- Run only the backend: `npm run server` from the root, or `cd server && npm run start`.
- Default ports are frontend `3000` and backend `5001`; the backend also honors `PORT`.
- Build the frontend: `npm run build`.

## Tests And Evaluation

- Backend test runner: `cd server && npm test`; this also validates the GitHub Actions quality gate workflow contract.
- Frontend test runner: `npm test` from the repo root. Watch mode: `npm run test:watch`.
- Default synthetic RAG eval: `cd server && npm run eval:synthetic`.
- Current tracked `latest.*` synthetic report uses the near-duplicate corpus: `cd server && npm run eval:synthetic -- evaluation/synthetic-corpus-near-duplicate.json`.
- Run a specific synthetic corpus: `cd server && npm run eval:synthetic -- evaluation/synthetic-corpus-compare-hard.json`.
- Chunking comparison corpus: `cd server && RAG_CHUNK_STRATEGY=structured RAG_CHUNK_OVERLAP=180 npm run eval:synthetic -- evaluation/synthetic-corpus-chunking.json`.
- Parameter sweep benchmark: `cd server && npm run eval:param-sweep`; use `-- --profile full` for the larger topK/overlap/rerank/hybrid matrix.
- Feedback corpus generation: `cd server && npm run feedback:corpus`.
- Feedback regression eval: `cd server && npm run eval:feedback`; this writes ignored `evaluation/generated/feedback-corpus.json` and `evaluation/results/latest-feedback.*`.
- Trajectory eval: `cd server && npm run eval:trajectory`; this writes ignored `evaluation/results/latest-trajectory.*` and checks skill selection, follow-up, clarification, access scope, budget behavior, and four pinned custom-Skill graph cases.
- Historical metrics viewer: `cd server && npm run quality:gate`; its PASS is not current-commit evidence.
- Current PR quality gate: `cd server && npm run quality:current`; it requires the `quality-current` profile plus fresh, clean, same-SHA synthetic/feedback/trajectory/planner/recovery evidence, validates versioned case/check/corpus/response contracts, binds citations to raw retrieval, independently recomputes claim support from pinned corpus pages, verifies deterministic upload identity and recovery cases, and compares only against the pinned deterministic baseline. Metrics remain `unverified` until worktree, lineage, report contracts, and baseline all pass. High-risk trajectory cases persist minimal privacy-safe `case.response.observed` facts; `check.detail` is diagnostic only. Response projections are stable report contracts, not runner-execution proof, content-digest proof, or full internal-event attestations.
- Strict release evidence gate: `cd server && npm run release:gate`; it requires the complete robust/planner/recovery/runtime/readiness report set to carry current-commit, clean-worktree, fresh, corpus/provider-consistent lineage. The guarded rollout evidence additionally requires a real-provider DAG planner case, guarded runtime smoke, and readiness checks; a local mock result is not real-model evidence. Use `-- --no-fail` only for diagnostics; it does not change a failing report to pass.
- Real-corpus eval expects a local corpus file created from `evaluation/real-corpus.example.json` or passed explicitly: `cd server && npm run eval:real -- evaluation/real-corpus.json`.
- Ragas eval runs against saved Node eval payloads: `cd server && npm run eval:ragas -- --input evaluation/results/latest.json`. It requires optional dependencies plus `OPENAI_API_KEY`; see `server/evaluation/ragas-requirements.txt`.
- Retrieval arm comparison: `cd server && npm run eval:retrieval-comparison` uses the deterministic hashed-TF embedding (plumbing only, never an effect claim). `-- --embedding-provider openai` runs real embeddings against any OpenAI-compatible endpoint (including local Ollama) and writes `latest-retrieval-comparison-openai.*` so it never overwrites the deterministic report; `--rerank-provider cross-encoder --cross-encoder-endpoint <url>` measures a neural reranker. Every split reports paired bootstrap 95% CIs; do not describe an arm difference as better unless its interval excludes 0.
- LLM call resilience: `cd server && npm run eval:llm-resilience [-- --no-fallback]` injects 429 (precise and coarse Retry-After), 503s, hanging requests, empty completions, and a down primary against a local fake OpenAI server; no model or key needed.
- Framework-only entry points (not yet run on real data, no tests): `npm run corpus:qasper -- --input <qasper-dev-v0.3.json>` converts a QASPER release into the corpus format; `npm run eval:judge -- --input <answers.json> [--labels <labels.json>]` is an LLM judge that reports agreement and Cohen's kappa against human labels. Do not quote judge scores that have not been calibrated.
- Interview-facing numbers live in `server/docs/interview/CURRENT-TRUTH.md` (Chinese) with their commands and commits; update that file first when a measured number changes.

Backend `npm test` runs `test/run.test.mjs`, which discovers every `server/test/*.test.mjs` file at runtime and runs them under `node --test` in per-file child processes; a new suite only needs to be dropped into `server/test/`, not registered anywhere. The typed-DAG suites include `agent-execution-graph.test.mjs`, `agent-execution-graph-runner.test.mjs`, `agent-dag-planner-adapter.test.mjs`, `agent-replanner.test.mjs`, `agent-replan-adapter.test.mjs`, `agent-custom-skill-stage.test.mjs`, `agent-authorized-catalog.test.mjs`, `agent-dynamic-skill-selection.test.mjs`, and `agent-execution-graph-checkpoint.test.mjs`. `app-planner-adapters.test.mjs` drives a background task through `createAppServices`; `runtime-smoke-graph-signal.test.mjs` tests persisted guarded-run evidence without external I/O. Concurrency assertions in graph suites use barriers and deferred promises; do not replace them with millisecond timing assertions.

`agent-execution-graph-postgres.integration.test.mjs` uses `PGVECTOR_TEST_DATABASE_URL` and a separate Node process to verify a persisted graph checkpoint resumes from the PostgreSQL agent-run store without replaying a completed write. The disposable `cd server && bash scripts/run-pgvector-integration.sh` runner includes it; without the database URL it is skipped, not passed.

## Implementation Notes

- Keep RAG changes inside `server/rag/` where possible; route/API behavior lives in `server/app.js`.
- AgentRAG skills are registered in `server/rag/skills/registry.js`; built-ins live in `server/rag/skills/built-ins.js`, and whitelisted custom skills live under `server/rag/skills/custom/`. Current custom skills include `extract_timeline`, `risk_review`, `summarize_contract`, and `compare_documents`.
- New skills need stable `id/version/label/budgetKey/requiresAccessScope`, deterministic `match()`, and an `execute()` path that receives `accessScope` when reading user/workspace data. Custom skills must be exported from `server/rag/skills/custom/index.js`; do not let the model call arbitrary unregistered tools. The model-facing atomic custom-Skill catalog in `server/rag/skills/authorized-catalog.js` is narrower: it requires explicit typed input/output contracts, declared effects, a scoped document input, and successful `getDocument(docId, accessScope)` checks for every selected document; an empty or unverifiable document set grants no catalog entries. It is independent of V1 intent `match()` and composite chains.
- Agent bootstrap/session setup lives in `server/rag/agent-bootstrap.js`; keep working memory creation, planning, selected skill ordering, run context creation, and skill tracker wiring there.
- Agent preparation flow lives in `server/rag/agent-preparation-flow.js`; keep plan trace, pre-execution clarification, query planning trace, and skill chain trace there.
- Agent run context lives in `server/rag/agent-run-context.js`; keep trace appending, budget snapshot helpers, agent trace recording, observability assembly, and clarification response orchestration there rather than rebuilding those cross-cutting helpers in `server/rag/agent.js`.
- Document RAG execution loop lives in `server/rag/agent-document-loop.js`; keep primary document RAG, self-check, gap analysis, follow-up retrieval, evidence clarification, and working-memory claim/gap updates there rather than expanding `server/rag/agent.js`.
- Non-document skill execution is exported through `server/rag/agent-skill-runners.js`; built-in runners live in `server/rag/agent-built-in-skill-runners.js`, custom skill chain execution lives in `server/rag/agent-custom-skill-runner.js`, and web search execution lives in `server/rag/agent-web-runner.js`. Keep those execution details out of `server/rag/agent.js`.
- The custom skill stage has two execution paths behind one seam. `server/rag/agent-custom-skill-stage.js` resolves `AGENT_SKILL_GRAPH_ROLLOUT` (`guarded` / `shadow` / `off`, default `guarded`; an unrecognized value resolves to `off`) and either runs the V1 sequential chain in `agent-custom-skill-runner.js` or the V2 typed DAG. Both paths return the same flat skill result array, emit the same `custom_skill` step type, and share one run store and one replay safety matrix; do not stand up a parallel runtime or a second run store. `guarded` falls back to V1 only when a graph is rejected before any node ran — there is deliberately no fallback after partial execution. The executor dial and the planner dial are separate: the DAG planner follows `AGENT_EXECUTION_PLANNER` and a failed LLM plan falls back to the deterministic graph rather than straight to the V1 chain, so `rollout:readiness` (zero fallback, zero mock/real divergence) measures pure-LLM planning and is not the gate for the executor default. Under `guarded` the LLM execution planner sees authorized atomic Skills and may add a `custom_skills` stage the intent did not select. Keep the V1 chain (whole-graph-rejection fallback and the `off` opt-out), the composite intents, and the deterministic planner.
- The V2 typed DAG is split across `server/rag/agent-execution-graph.js` (versioned graph contract plus the pure-function validator/compiler), `agent-execution-graph-runner.js` (stable topological scheduler, runtime concurrency cap, atomic budget reservation, side-effect serialization, node run records, and runtime input/output schema gates), `agent-dag-planner-adapter.js` (redacted whitelist-only planning surface that emits atomic skill nodes rather than composite chain ids), and `agent-replanner.js` (bounded patch-only replan, `maxReplans: 1`). Every initial plan and every replan patch goes through the same validator, which accepts or rejects a graph whole so an illegal graph never partially executes. The runner also validates resolved input before budget/execution and actual output before downstream binding, including reused checkpoint output. Node inputs bind only to validated request fields or upstream node outputs; do not reintroduce concatenated free text as the primary data interface. The planner never decides scope, `docIds`, approvals, budget, concurrency, or retry limits — the runtime owns those. This DAG covers custom Skills only, not the outer document/web/built-in/capability stages.
- The heterogeneous v3 DAG migration is frozen at shadow (decision and unfreeze conditions in `docs/unified-agent-dag-migration.md`); do not wire its execution path without that bar being met. It is separate from the production custom-Skill path. `skills/unified-graph-catalog.js` builds a scoped all-stage candidate catalog; direct Capability adapters enter only through trusted `allowedCapabilityIds`. `agent-unified-dag-planner.js` validates injected proposals against its narrowed registry; `agent-unified-graph-shadow.js` records a redacted `unified_graph_planned` event on real `/chat` and background tasks only when `AGENT_UNIFIED_GRAPH_ROLLOUT=shadow` (default `off`). There is deliberately no v3 `guarded` setting or default model adapter yet; `executionWired: false` and `agent-unified-graph-projection.js` are not proof that all-stage execution, approval continuation, finalization, or recovery is live. `document_evidence_check` is a graph-only deterministic built-in; V1 document self-check/follow-up stays in `agent-document-loop.js`. See `docs/unified-agent-dag-migration.md` before widening the rollout.
- Skill contract metadata lives in `server/rag/skills/skill-contract.js`: `inputSchema`, `outputSchema`, `effects`, `idempotency`, `parallelSafe`, and `replaySafe` on top of the existing `id/version/label/budgetKey/requiresAccessScope/match/execute`. Skills that declare none of it get safe read-only defaults for V1 compatibility, but inferred defaults do not admit a Skill into the model-facing graph catalog. The current typed output is an answer envelope (`text`, `citations`, `abstained`), not a separately verified semantic delta/risk object. `describeSkillReplayContract()` is persisted onto every `custom_skill` step by both execution paths, because recovery is handed the stored step and never the live skill; a persisted declaration may only narrow a replay verdict, never widen it, and `custom-research-steps.js` rechecks the live registry contract before replaying so a stale or forged declaration cannot fail open.
- The outer `document_rag`, `follow_up_retrieval`, and built-in `research_question` steps call `ragService.chat` with live session/user identity and may write session or long-term memory. Their V1 step inputs persist `effects: workspace_write`, `idempotency: adapter_defined`, and `replaySafe: false`; the replay matrix rejects unattended replay even for older steps without metadata. Explicit `retry_failed_step` remains available but may repeat memory writes and is not an exactly-once guarantee. Do not describe these steps as read-only RAG or use them as auto-recovery-safe fixtures.
- Graph observability is an agent run event (`type: "skill_graph_planned"` via `recordExecutionGraph`), not a `/chat` response field. Keep `graph`, `nodeRuns`, and `replans` as versioned additive fields on run events so the `/chat`, `agentObservability`, frontend trace, feedback, approval, recovery, and evaluation report contracts stay backward compatible.
- Guarded graph checkpoints live privately in the existing agent run store (`server/rag/agent-execution-graph-checkpoint.js`), not in the public run projection or a new store. Resume must verify owner/digest, current registry contract, persisted steps, and already-charged budget before reusing completed nodes; unknown in-flight work and mismatches require manual recovery. This includes an in-flight `readOnly` Skill: storage alone cannot prove its former worker has stopped. Startup auto recovery may use the dedicated `resumeAgentExecutionGraphRun()` path only at a node boundary, for a stored outer plan containing exactly `custom_skills`, no pending approval, and a reconciled guarded checkpoint. It must claim that checkpoint once and must not regenerate Intent or the outer execution plan. An ordinary `runAgentRag` re-entry must reject any run with a graph checkpoint in the same run-revision CAS as its snapshot update, even if the request and owner match; only the dedicated recovery path may resume it. The claim, guarded node start, and run completion/failure must also fence stale workers through run-revision CAS. A second worker must skip an already-claimed graph without mutating its status; an abandoned claim is never replayed automatically and requires operator investigation.
- Generic single-step retry/resume (`agent-run-step-executor.js`) must reject a guarded `custom_skill` graph node before changing run or step state. The pure graph replay guard is also enforced inside the run store CAS for standalone retry, approval, and step transitions, closing preflight-to-mutation races. A post-graph outer step or approval is allowed only when its durable event proves it was created after the matching terminal graph event. Graph node start and settlement both carry the graph recovery claim; do not turn either into an unfenced generic step transition. Keep legacy V1 custom-step replay behavior unchanged.
- Agent planning and skill-chain selection live in `server/rag/agent-planner.js`; keep request classification, planner actions, chain ordering, and pre-execution clarification checks there rather than adding them back to `server/rag/agent.js`.
- Agent trace formatting lives in `server/rag/agent-trace.js`; keep trace step summaries and compact trace serialization there when adding new trace step types.
- Planner structured outputs: intent, execution, and DAG planner calls send a per-request strict JSON Schema `response_format` built from the runtime whitelist (`server/rag/structured-output.js` helpers, builders next to each planner prompt). Keep every free-text field bounded with `pattern` and every array with `maxItems` (an unbounded rationale ran to thousands of tokens under constrained decoding); strict mode documents `pattern`, not `maxLength`. The schema only narrows output: validators stay the final authority, parsers keep the first complete JSON value because some servers do not hard-enforce the schema, and `RAG_STRUCTURED_OUTPUT_ENABLED=false` falls back to prompt-only JSON.
- Model output source labels are normalized as the text arrives (`normalizeGroupedSourceLabels` in `answer-writer.js`), so `[Source 1, Source 3]` reaches self-check, finalizer, and citation projection as one label per bracket. Variant file names such as `vendor-a.pdf` count as document labels in claim attribution (`self-check/attribution.js`); keep the topical-file-name protection and never add a shared stem as an alias of sibling documents.
- LLM call resilience lives in `server/rag/openai.js` / `openai-client.js`: jittered exponential backoff, `retry-after-ms` / `Retry-After` as a floor, `RAG_LLM_REQUEST_TIMEOUT_MS` timeouts retried as transient, one retry for an empty completion, and failover to `OPENAI_CHAT_FALLBACK_MODEL` only through the model registry (so workspace policy applies) and only for transient errors. Each model tried is metered as its own LLMOps event and the returned `modelRoute` names the model that answered. Every HTTP request to a model (chat and embeddings, including each retry) also passes `server/rag/model-call-guard.js`: a per-endpoint-and-model concurrency cap (`RAG_LLM_MAX_CONCURRENCY`) and a consecutive-failure circuit breaker (`RAG_LLM_CIRCUIT_FAILURE_THRESHOLD` / `RAG_LLM_CIRCUIT_COOLDOWN_MS`). Only unavailable errors (5xx, 408, timeouts, connection failures) count toward the breaker, never 429 or other 4xx. An open circuit throws `CIRCUIT_OPEN` (503), which is never retried on the same model but is failover-eligible. Guard state is per process; the resilience eval resets it before each scenario.
- OpenTelemetry tracing: `server/rag/tracing.js` depends only on `@opentelemetry/api` (a no-op until an SDK is registered); `server/otel.js` registers the SDK when `OTEL_TRACING_ENABLED=true`, exporting OTLP/HTTP as protobuf by default (Phoenix rejects JSON) or JSON via `OTEL_EXPORTER_OTLP_PROTOCOL`. Spans follow the GenAI semantic conventions: `invoke_agent archive_rag` per run (in `agent.js`), `agent.plan *` per planner, `execute_tool <skillId>` in `executeObservedSkill`, and `chat|embeddings <model>` in `runWithLlmOpsMetric`; agent steps are `agent.step` events. Never put questions, prompts, model output, or document text in span attributes or events; `test/tracing.test.mjs` checks for leaks. `agentObservability.traceId` appears only while a span is recording. `npm run trace:demo [-- --real] [-- --otlp]` prints one run's span tree.
- Run-level usage ceilings live in `server/rag/run-usage.js`: tokens, estimated cost, and wall-clock time per `runAgentRag` / graph-resume invocation (`AGENT_RUN_MAX_TOKENS`, `AGENT_RUN_MAX_COST_USD`, `AGENT_RUN_MAX_DURATION_MS`, or `maxRunTokens` / `maxRunCostUsd` / `maxRunDurationMs` in `agentBudget`; 0 disables). Usage is charged in `recordLlmOpsMetric` from successful model calls only, and the run is found through `AsyncLocalStorage`, so do not thread a usage object through call sites. Enforcement stays inside `consumeBudget` / `reserveBudget` / `getRemainingBudget` so every tool degrades through its existing `budget_limit` path; `traceSteps` is exempt. Keep the meter under `budgetState.run` and `agentObservability.budget.run`: `budget.limits` / `budget.used` and the graph checkpoint owner budget must keep their shape.
- `POST /chat/stream` streams agent progress over SSE through an `AsyncLocalStorage` sink (`server/rag/agent-event-stream.js`); emit only compact step summaries (never step detail). Raw answer tokens never leave the server: `server/rag/answer-drafts.js` streams the primary document answer from the model, runs the finalizer's claim check (`evaluateClaimSupport` + heading normalization) on each completed prefix, and sends only supported sentences as `answer_draft` events, formatted with the finalizer's `formatSupportedClaim`; a retried or failed-over model call sends `answer_draft_reset`. A sentence counts as complete only after its trailing `[Source N]` labels and the next character arrive. Drafts are opened only by `runWithAnswerDraftChannel` around the primary `document_rag` call and only when a streaming sink is attached, so `/chat`, tasks, evals, Skill-internal calls, and follow-up retrieval never draft. Drafts are provisional (the loop may ask for clarification or replace the answer); the final `result` event must stay identical to the `/chat` status and body. `npm run eval:answer-drafts` measures draft timing and retention with a real model.
- Agent run-scoped working memory lives in `server/rag/agent-working-memory.js`; preserve query dedupe, claim support updates, unresolved/resolved gap handling, and execution loop counters there rather than adding state mutation back to `server/rag/agent.js`.
- Agent skill execution observability lives in `server/rag/agent-skill-observability.js`; keep per-skill attempts, duration, citations, abstain, retry/follow-up, budget, run records, and skill trace detail construction there.
- Agent answer synthesis lives in `server/rag/agent-synthesis.js`; keep direct answer mode detection, skill-chain answer composition, and finalizer eligibility there.
- Agent finalization flow lives in `server/rag/agent-finalization-flow.js`; keep agent mode resolution, source selection, answer synthesis/finalizer invocation, finalizer trace, final response assembly, and final agent trace recording there.
- Agent chat response assembly and evidence clarification payloads live in `server/rag/agent-response-builder.js`; preserve `/chat` response fields, status code behavior, and error wording there rather than rebuilding response objects in `server/rag/agent.js`.
- AgentRAG query planning lives in `server/rag/agent-query-planner.js`; document/custom skills should pass `retrievalPlan` through to `ragService.chat`, and RAG observability should preserve `agentRetrievalPlan` plus actual `retrievalQueries`.
- Agent self-check claim support and structured gap analysis live in `server/rag/agent-self-check.js`; final answer filtering lives in `server/rag/agent-finalizer.js`. Keep both deterministic and preserve `claimSupport`, `gap_analysis`, and follow-up loop metadata in agent trace, feedback records, and feedback corpus metadata.
- Clarification gate behavior lives in `server/rag/agent.js`; when the agent needs user input it returns `agentMode: "clarification"` with `clarification.reason`, `clarification.question`, and a `clarification_gate` trace step instead of throwing for ordinary scope issues.
- Agent working memory is run-scoped and must not be written to long-term memory unless explicitly requested; preserve `agentWorkingMemory` and `agentObservability.workingMemory` when changing execution, feedback records, or feedback corpus metadata.
- Skill chaining is whitelist-only in `server/rag/agent.js`; preserve `agentObservability.skillChain`, the `skill_chain` trace step, accessScope propagation, and per-skill budget checks when adding or changing chains.
- Agent trace UI lives in `src/components/RenderQA.js`; preserve the display of selected skills, skill chains, retrieval queries, evidence gaps, unsupported claims, and finalizer-removed claims when changing `/chat` response shape or frontend rendering.
- Trajectory eval lives in `server/evaluation/trajectory-eval.js`; preserve checks for skill selection, follow-up retrieval, clarification gate, accessScope propagation, and budget limits when changing agent orchestration. The four `skill_graph` cases in `server/evaluation/trajectory/cases/skill-graph.js` pin `AGENT_SKILL_GRAPH_ROLLOUT` per case through `withEnvironmentOverrides` and read the `skill_graph_planned` run event. `server/evaluation/planner/cases/index.js` also pins a guarded `planner_dynamic_skill_graph` case: compare-only upstream intent, independent atomic compare+risk DAG, scope and observability checks; the `real` provider exercises the LLM DAG planner. Every trajectory/planner case id, check id, and response projection is pinned in `server/evaluation/quality-current-suite-manifest.js`, so adding or renaming a case or check means updating that manifest and bumping its version in the same change.
- Observability reporting lives in `server/evaluation/observability-report.js` and `server/evaluation/build-observability-report.mjs`; preserve support for both `traceType: "agent"` events and lower-level RAG trace events. The `recovery` block counts `skill_graph_planned` run events (planned, executed, fallback, fallback-after-execution, reused nodes, applied replans) and guarded graph startup resume signals. `server/evaluation/recovery-observability-eval.js` produces the replan signal from a real guarded run and the `skill_graph_startup_resume` case from a checkpoint plus re-instantiated services over one in-memory store. That case exercises the production continuation API but does not prove an OS process restart or PostgreSQL durability; `quality-recovery-gate.js` fails when recovery checks fail or a graph falls back to V1 after a node has executed.
- Quality gate assembly is split across `server/evaluation/quality-*.js`; keep `quality-report.js` as the compatibility export surface, result file I/O in `quality-result-reader.js`, run summaries in `quality-run-summary.js`, per-eval gates in their matching `quality-*-gate.js` modules, and final gate composition in `quality-combined-gate.js`.
- AgentRAG optimization order is documented in README under "AgentRAG 优化路线"; continue in that order unless the user explicitly reprioritizes it.
- `/chat` returns `agentObservability` with per-skill selected status, attempts, duration, citations, abstain, retry/follow-up, budget, execution loop, working memory, skill chain, clarification gate, and error metrics. Preserve it when changing agent execution, feedback records, or feedback corpus metadata.
- API auth is controlled by `API_AUTH_ENABLED` plus either `API_AUTH_TOKEN` for single-token local use or `API_AUTH_TOKENS` for per-user/per-workspace token mapping; the frontend can send `VITE_API_AUTH_TOKEN`, which becomes an `x-api-key` header.
- When auth is enabled, document list/chat/delete/file access is filtered by the authenticated token's `userId` and `workspaceId`; keep new document routes scoped the same way.
- `VECTOR_STORE_PROVIDER=pgvector` is the default: chunks and vectors live in PostgreSQL (`server/rag/vector-store-pgvector.js`, migration `server/db/migrations/012_create_rag_document_chunks.sql`, local instance via `docker-compose.yml`). `local` and `qdrant` remain explicit opt-ins; any other value fails closed at health, ingest and search -- never add a silent fallback. Document RAG runs the dense and sparse routes independently by default (`RAG_HYBRID_ENABLED=true`, `RAG_HYBRID_FUSION=rrf`); rerank stays after fusion, and the sparse route on pgvector is PostgreSQL FTS ranked with `ts_rank_cd`, which must not be described as BM25. The pgvector ingest path registers the document row and writes its chunks in one transaction (`rag/index.js`); keep it that way. `npm run vector:reindex` (dry run by default, `--apply` to write) backfills pgvector from a local index, Qdrant, or the registry's PDF bytes.
- Retrieval results carry `provenance` (route, raw rank/score, fusion, retrieval queries) and `/chat` responses carry an additive `retrieval` block (provider, whether each route executed, candidate counts). Synthetic evaluation reports record it as `summary.retrieval` and per-case `retrieval`; `quality:current` and the robust gate fail when it disagrees with the manifest or when a route did not actually run. Keep `summary.config` unchanged by these fields: the pinned deterministic baseline's regression profile key is built from `config`.
- Suites that exercise the local JSON index (`test/rag.test.mjs`, `test/app.test.mjs`) pin `VECTOR_STORE_PROVIDER=local` themselves. The real-database suite is `test/vector-store-pgvector.integration.test.mjs`; it runs only when `PGVECTOR_TEST_DATABASE_URL` is set (CI provides a `pgvector/pgvector:pg16` service) and is reported as skipped otherwise, never as passed.
- Startup health checks report OpenAI, auth, vector store, PostgreSQL document/session stores, and long memory. `STARTUP_HEALTH_STRICT=false` allows the server to start while reporting health errors.
- For RAG debugging, `RAG_OBSERVABILITY_ENABLED=true` writes JSONL traces under `server/data/rag-observability/`; set `RAG_OBSERVABILITY_INCLUDE_CONTEXT=true` only for local debugging when full chunk text is acceptable.
